## 0. 结论：不建议上线（No-Go）

**共确认 3 项阻断（Blocker）、12 项高风险（High）、约 18 项中风险（Medium）。**

本轮最关键的判断不是"又发现了一个注入点"，而是：

> **当前磁盘上的部署产物无法被证明来自当前源码，而用于证明它的自检脚本会在关键分支里丢弃全部校验结果。**
> 合约无管理员、不可升级、体积逼近 16,384 B 上限，一次错误部署不可逆。

三类阻断分别是：

1. **部署产物可验证性断裂**（B-1）——实测 `action` 为 **16,201 B**，而"部署参数唯一依据"写 **16,300 B**；`verify_build.py` 在 manifest 缺失（当前正是这种状态）时提前 return 并丢弃 nonce / BURN_ADDR / ACTVIEW 全部校验；`SHA256SUMS.txt` 未覆盖 deploy.json、contractmap、fitsh；"唯一依据"文件还在描述一个源码里根本不存在的 `hacd_info` 占位实现。
2. **PC 钱包主进程端点白名单可被渲染层改写**（B-2）——`cfg:save` 与 `isAllowedEndpoint` 共用同一份可写配置，且大量 HTTP 通道（含把已签名交易 POST 出去的路径）根本没有校验；`liq:*` 甚至直接接收渲染层传入的 `indexer`。
3. **口令钱包私钥 = 单轮 SHA-256(口令)**（B-3）——PC 与 Android 双端一致，无 salt、无迭代、无强度下限，可离线批量枚举口令派生地址盗币。

**放行条件**：§8 的"部署前硬门禁"全部关闭，并以当前源码重跑编译 + 差分测试 + 修正后的自检；在此之前不建议执行 ContractDeploy 或分发安装包。

### B-2　PC 钱包端点白名单可被渲染层改写，多条通道未校验（已签名交易/私钥外带）

**证据**（`wallet-app/main.js`）：

```js
// :305-319  sanitizeCfg 只校验协议
if (u.protocol !== 'http:' && u.protocol !== 'https:') return null;
// :337-344  cfg:save 把渲染层传来的配置写盘
saveCfg(Object.assign({}, cur, clean));
// :364-375  白名单的来源正是同一份可写配置
const cfg = loadCfg() || {};
const allowed = [cfg.node, cfg.indexer, 'https://explorer.hacash.org'] ...
return allowed.includes(t.origin);
```

- `isAllowedEndpoint` 全文件**只有 2 处调用**：`http:get`（`:379`）、`tx:broadcast`（`:697`）。未校验的通道包括：`:905` / `:951` redeemBatch 把**已签名交易** `POST /submit/transaction`、`:714` `tx:translate`、`:507` `tx:check`、`:490` `fetchMinPurity`、`:1003` `srvGet`、`:1087` `contract:call` 等。
- `liq:sync / snapshot / watch / probe`（`:1008-1065`，本轮亲验）直接使用渲染层传入的 `req.indexer`，完全不经过白名单 → 一步 SSRF（含 `http://169.254.169.254` 云元数据、内网端口探测）。
- `keyPath` 类通道（`:356-359`、`436-437`、`746-757`、`770-771`）未走 `safeWalletPath`，把任意路径交给 txbuild 子进程读取 → 本地任意文件读取原语。
- 触发链真实存在：`renderer/app.js:2640-2653` 钱包列表把 keystore 的 `address` / `label` / `f.path` 未转义拼进 `innerHTML` 与属性（C-H3 同类遗漏）；`BrowserWindow`（`:1274-1293`）`will-navigate` 仅判断 `url.startsWith('file://')`，UNC/SMB 形式的 `file://host/share/...` 可绕过。

**影响**：渲染层一旦被 XSS 或导航劫持，可改写端点白名单、把已签名交易 POST 到攻击者地址、让主进程读取任意文件，进而外带会话私钥。项目源码注释（`:296-304`）已自承"渲染层能改写 node 使校验一起失效"，但采用了"UI 看得见"的折中，未做进程隔离。

**修复**
1. 端点白名单改为主进程**硬编码常量**，`cfg:save` 不得改写 origin；拒绝环回 / 内网 / 链路本地段（127/8、10/8、172.16/12、192.168/16、169.254/16、::1、fc00::/7）、IP 字面量与任意端口；防 DNS rebinding（校验解析后 IP）。
2. 把校验**下沉**到 `httpGetJson` / `httpPost` / `srvGet` 统一入口，覆盖所有 handler；`liq:*` 一律走同一白名单。
3. 所有 handler 校验 `event.senderFrame.url()` 为本地 file URL、对 req 做类型/schema 校验；`keyPath` 复用 `safeWalletPath` + 用户亲手选过集合。
4. 修 `renderer/app.js:2640-2653` 转义；`will-navigate` 改为精确比对 `pathToFileURL(index.html).href`，显式 `webSecurity:true` / `allowRunningInsecureContent:false`，`setPermissionRequestHandler` 全 deny。
5. 强制 https（保留 localhost 调试开关），与 Android 侧 H-10 同步整改。

### B-3　口令钱包私钥 = 单轮 SHA-256(口令)，双端一致，可离线爆破

**证据**

```js
// wallet-app/keystore.js:36-38
function secretFromPassword(password){ return crypto.createHash('sha256').update(...).digest(); }
// wallet-app/main.js:531-533  kind === 'password' -> secret = ks.secretFromPassword(label)
```
```kotlin
// android-app/.../wallet/Keystore.kt:52-55
fun secretFromPassword(password: String): ByteArray =
    MessageDigest.getInstance("SHA-256").digest(password.toByteArray(Charsets.UTF_8))
// AppViewModel.kt:49-57  passphrase 只要求非空；加密口令 password 在 saveWithVault 路径中根本未使用
```

- 无 salt、无迭代、确定性派生；`WalletScreen.kt:169` 校验的 6 位长度是"加密口令"框，不是作为私钥来源的 passphrase。
- 攻击者可离线枚举常见口令 → 派生地址 → 查链上余额，命中即盗币；无需接触设备、无需突破 Keystore。
- PC 端 scrypt 默认 `N=2^15`，且 `keystore.js:64-68` 解密时直接采用文件自带的 `n/r/p/dklen`（无范围白名单），恶意 keystore 可造成 CPU/内存 DoS。

**修复**
- 口令钱包改为「**随机私钥 + 标准 KDF（scrypt N≥2^15 / Argon2id）+ 随机 salt** 加密」，不再由口令直接决定私钥；强制 passphrase 最小熵（≥12 字符 + 字符集）并明示"口令即私钥"风险。
- 过渡方案：上线版本中**禁用/隐藏口令钱包入口**，仅保留 keystore 与硬件加密路径。
- 统一 PC / Android 派生算法与迁移策略；decrypt 前把 KDF 参数限定在固定白名单。
