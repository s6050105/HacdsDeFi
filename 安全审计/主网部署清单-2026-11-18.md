## 零、先看这一页

整个部署是 **6 个链上动作 + 2 个运维动作**，顺序不能错：

```
链上：① 发行 4000 资产  ② 发行 4001 股权  ③ 部署合约 A  ④ 部署合约 B
```

| 参数 | 值 | 说明 |
|---|---|---|
| supply | `10000` | `vault.fitsh` 的 `SHARE_TOTAL`，**发行上限** |
| decimal | `0` | |
| **issuer** | **`15fv6cNE…`（部署者自己）** | ⚠ **绝不能填合约 B！见下方警告** |
| ticket / name | `HACDSV` / `hacdsv` | 展示用，不影响逻辑 |

发行后 10,000 份**全在部署者名下**，需线下分给股东。
股东必须**质押进合约 B** 才开始计息（见 §5.3）。

> ⚠ **B 没有发行能力**（Action 是 TopOnly，无 AssetCreate）。
> 这 10,000 份就是全部，**发错数量无法重发**。
>
> ## ⚠⚠ 2026-11-18 实际事故记录（第二次踩同一个坑）
>
> 第一轮部署时，`issuer` 被填成了**合约 B 的地址**（理由是"股权归属金库合约"，
> 那是把 hacds 的 issuer 逻辑机械套用过来的错误类推）。结果：
>
> | 项 | 值 |
> |---|---|
> | 合约 B 链上 3001 余额 | **10,000** |
> | 合约 B 的 `sh:` 账本 | **0** |
> | 后果 | `PermitAsset` 永远 `return 11`，**再也转不出来** |
>
> `AssetCreate` 是**凭空铸造并直接打到 issuer 地址**的，不触发任何钩子，
> 所以 `PayableAsset`（唯一能建 `sh:` 账本的入口）根本没被调用过。
>
> 而 B 一共 15 个 external 函数里，**没有任何一个能初始化 `sh:` 账本**
> （`claim` / `pay_rent*` / 视图函数都不行），所以这是死锁，无法从链上补救。
>
> **代价**：serial 3000/3001 永久作废（不可重发），两个合约换 nonce 重部署，
> 多发两笔 AssetCreate，合计约 36 HAC。
>
> **教训**：`issuer` 回答的是"这批资产**诞生在哪里**"，
> 不是"这批资产**最终归谁管理**"。对于需要质押进合约的凭证型资产，
> 必须发行到**能自由转出的普通地址**（部署者），再由持有人自己质押。

## 三、运维动作（部署后立刻做，别拖）

### ⑤ 首注建池

```bash
hacds_txbuild call <部署者> <ts> bw2sRCNPw3DsvAyS9o8CeMbJJhQ9NJ37h \
  add_liquidity  "<hac_zhu>:u128,<ds_atoms>:u128,0:u128,0:u128"
```

**门槛**：`share = isqrt(hac_amt × ds_amt)` 必须 `> MINIMUM_LIQUIDITY = 1000`，
否则 `return 26`。建议首注 **≥ 1,000 HAC + ≥ 100 亿 hacds**。

> **单侧上限 `LP_MAX_SIDE = 10¹⁸`**，防 `hac × ds` 溢出 u128。正常量级远达不到。

首注会创建 **24 个固定键 + 4 个地址键**，全部按 `PERIOD_NEW = 100` 期租：
100 期 × 100 块 = **10,000 块**。

| 环境 | 出块间隔 | 10,000 块 = |
|---|---|---|
| 主网 | **300 秒** | **34.7 天** |
| 测试网 | 1 秒 | 2.8 小时 |

### ⑥ 立即 topup（这一步千万别省）

```bash
HACDS_KEEPER_KEY=/path/keeper.key \
python3 hacds_server-main/hacds_exchange/indexer/hacds_keeper.py topup \
  --node http://<NODE>:8082 \
  --contract bw2sRCNPw3DsvAyS9o8CeMbJJhQ9NJ37h \
  --main <首注人地址>
```

**为什么必须手动跑一次**：`rent_keys` 的触发条件是 `live < period/3 = 100 块`，
而新键 `live = 10,000 块`。**34.7 天内 keeper 一次都不会触发**。
这段时间里只有 `topup_keys` 能救（不看阈值、直接补期）。

补完后租期从 100 期 → 300 期（≈ **104 天**），`rent_keys` 才开始正常工作。

> ⚠ 键到期后：`recover_credit = 0`（`storage_new` 传的就是 0），
> 所以 live 耗尽后**没有恢复窗口**，键被物理删除。
> 用户的余额 / LP 份额 / due 配额**永久归零**。测试链上真实发生过两次。

成本约 0.001 HAC（不付 keeper 报酬，只有手续费）。

### ⑥-b B 的键怎么办 —— ⚠ 现有 keeper 覆盖不到

**这是一个必须在部署前决定的问题，不是部署后再说的事。**

`hacds_keeper.py` 现在只认合约 A：

| 能力 | A | B |
|---|---|---|
| `rent_keys(keys, klen, period)` | ✅ 有 | ❌ **没有** |
| `topup_keys(keys, klen, period)` | ✅ 有 | ❌ **没有** |
| `rent_key_group_count()` / `rent_key_len_at()` / `rent_keys_group()` | ✅ 有（7 组） | ❌ **没有** |
| 给 keeper 付酬 | ✅ `tre:hac` | ✅ `reserve:rent`（`pay_keeper`） |
| 续租入口 | 按 klen 批量 | **只能按单个键** |

B 只有三个续租入口，且**都不接受"键清单"参数**：

| 入口 | 续什么 | 谁能调 | 上限 |
|---|---|---|---|
| `claim()` | 只续**调用者自己**的 `chk:/due:/sh:` | 本人 | 3 个键 |
| `pay_rent(period)` | 只续 B 自己的 `rpu:share/reserve:rent/tot:div` | 任何人 | 3 个键 |
| `pay_rent_ahac(group, period)` | 续**A** 的某组键（跨合约调 A 的 `topup_keys`） | 任何人 | 每组 ≤9 键 |

**所以 B 的股东地址键（`chk:/due:/sh:<addr>`）没有第三方批量续租的手段。**

#### 这意味着什么

`PERIOD_NEW = 100` 期 = 10,000 块 = **主网 34.7 天**。股东如果 34.7 天不 claim：

```
chk:<addr> / due:<addr> / sh:<addr> 到期 → 物理删除
```

后果按严重性排序：

| 键 | 丢了会怎样 |
|---|---|
| `sh:<addr>` | **质押份额归零** → `PermitAsset` 返回 11 → **链上的 4001 永远转不出来**（合约账本没了凭据） |
| `due:<addr>` | **已结算待提现的 HAC 归零**（钱还在合约里，但没人能证明是他的） |
| `chk:<addr>` | 下次 claim 时重新初始化 → 从该时刻起重新计息（历史增量作废） |

测试链上 9,690 份 3001 曾这样锁死；**第二轮部署时整批 10,000 份又因同类错误锁死一次**（见 §2 ② 的警告）。

#### ✅ 已选方案 C 并已实现（2026-11-18）

**改动已完成并编译通过**，只新增一个函数，没有改动任何既有逻辑：

```fitsh
function external pay_rent_shares(addrs: bytes, period: u128) -> u32 {
    // addrs = 连排的 21 字节地址；size % 21 == 0
    // 每个地址续 chk:/due:/sh: 共 3 键（不存在的跳过，靠 rent_one 内部判断）
    // 单笔地址数随 period 现算，超了就 return 60 让调用方分批
}
```

| 项 | 改动前 | 改动后 |
|---|---|---|
| action 字节数 | 2,333 B | **2,333 B** |
| 部署费 | 9.9083 HAC | **9.9486 HAC** |
| 外部函数数 | 33 | **34**（只多 `pay_rent_shares`） |
| 丢失的函数 | — | **无**（已逐项比对 contractmap） |

**单笔容量随 period 变化**（`storage_rent` 成本 = 36 × period × 键数，
桶上限 111,911）：

| period | 每地址成本 | 单笔地址上限 | 续满后租期（主网） |
|---|---|---|---|
| 30 | 3,240 | 34 | 10.4 天 |
| **100（keeper 默认）** | 10,800 | **10** | **34.7 天** |
| 300 | 32,400 | 3 | 104 天 |

合约侧与 keeper 侧用**同一个公式**现算，`selftest` 里固化了三档的回归断言
（含「多装 1 个就必然超桶」，防止上限写得过于保守白白多跑批）。

> **为什么不能用方案 A（keeper 代签 claim）**：`claim()` 内部是
> `var who = tx_main_addr()`，而 `tx_main_addr()` 是**交易发起者**。
> keeper 代签时发起者是 keeper 自己，只会续租 keeper 的键。
> `storage_rent` 又只在当前 frame 的 context_addr 上生效，跨不了地址。
> 「第三方替别人续租」在旧版 B 上根本没有入口 —— 这就是必须改合约的原因。

#### keeper 侧已同步改好

`hacds_keeper.py` 新增 `--vault` / `--vault-period`，daemon 每轮在续完 A
之后单独跑一段续 B（**B 失败不影响 A 的续租结论**）：

（不是键 —— 因为 B 自己拼 `chk:/due:/sh:`）。

`selftest` 已加 7 条断言覆盖这个新逻辑，全绿。

### ⚠ 第 6 项要特别小心

A 的 `PermitHAC` 里 TREASURY 分支**只校验 `cp == TREASURY`，不校验调用者身份**——
意味着**任何人都能发起清扫**。B 的设计规避了这个风险：`PayableHAC`
**完全不读 `tx_main_addr()`**，只按全局 `rpu:share` 累加器分摊，
所以第三方清扫拿不到任何好处（测试链已实测确认）。

**这条是 B 的记账方式不能改的唯一前提。** 验证方法：

### 5.3 部署后的第一次真实测试

用一个**小额**地址走完整流程：

```
1. 拿少量 4001（部署者转 1~10 份给测试地址）
2. 钱包里应出现金库卡片（金色），显示「钱包持有 N 份 / 已质押 0 份」
3. 点「立即质押」→ 质押 1 份
   → 卡片应仍在（靠 get_shares > 0 判定，不是靠钱包余额）
4. 从别的地址往 B 打一小笔 HAC（例如 1 HAC）
   → 200 续租 / 800 分红
5. 点「领取并提现」→ 钱包 HAC 应实际增加
6. 核对「待结算 / 待提现 / 总计可提取」三个数字
   → claim 之后「总计可提取」数值**不变**（增量转成了 due），这是正确行为
```

第 6 条是最容易被误判成 bug 的地方。设计文档 §4.1 专门讲了这一点。

## 七、回滚与应急

合约**不可升级、无管理员、无 pause**。所以：

| 场景 | 处置 |
|---|---|
| 部署后发现合约有 bug | **无解**。只能部署新 nonce 的新合约，并让用户迁移 |
| 市值 / 池子异常 | 没有暂停开关。只能靠公告 + 用户自行撤池 |
| keeper 挂了 | 账本键到期后**永久删除**。这是最严重的运维风险，必须监控 `keeper_health.json` |
| 资产发行参数写错 | **无解**，supply 与 decimal 不可改 |

**唯一可用的保险是部署前的自检**（`verify_build.py`）和部署后立即的验证清单。
这也是为什么 §1 花了 30 分钟做只读检查。
