## ✅ 第 5 步：H-2 运维闭环（A-67 ~ A-69）

### 先核实了 keeper 的现有设计

| 项 | 现状 | 结论 |
|---|---|---|
| 运行方式 | `run` 跑一轮就退出，计划任务**每小时**驱动 | 不是常驻服务 |
| 续租阈值 | `live < period/3`（period=300 → 100 块） | — |
| 检查间隔 | 每小时 = 12 块 | **12 块 ≪ 100 块，安全** |
| 首注处理 | `topup` 补到 300 期（104 天） | 覆盖首注后的空窗 |

**结论：keeper 的参数和调度方式本来就是对的，不需要改。**我一度以为"每 300 块检查配 period=300 会漏"，核实后发现实际是每小时一轮（12 块/轮），离阈值很远。

### 真正的缺口：可观测性

审计 H-2 说的是「`self_check` 没有租期告警位」。核实后发现更根本的限制：

**链上查不到单个存储键的剩余租期。**
- `storage_stat` 是 VM 内置，只能在合约函数内部调用
- 合约 A 有 `rent_keys_group()` 返回键清单，但**没有**返回租期的视图
- 节点 `/query/contract/storage/*` API 只给全局存储费参数

所以运维侧只能用**间接信号**：keeper 上一轮什么时候跑的。

| 改动 | 文件 |
|---|---|
| `_execute()` 结束时写 `keeper_health.json`（时间戳、成功/失败批次、键数、period、连续失败轮数） | `hacds_keeper.py` |

**四种状态**：

| status | 含义 | 处置 |

### ⚠ 发现合约 A 的设计问题（待决策）

**`tre:hac:`（金库累积额）在常态下永远不会增长。**

原因链：
```
swap 手续费 20% → apply_reserve()
  ① 先补 def:hac:（赤字）
  ② 再补 res:hac: 到 3% × providers   ← 吃掉绝大部分
  ③ 剩余才进 tre:hac:
```
而每笔 swap 让 `providers` 涨 X、目标涨 0.03X，手续费只注入 `res` 0.001X ——
**目标涨速是注入的 30 倍**，`res` 永远追不上。

唯一能让 `tre` 涨的路径：**清算协议费直接 `+=` 到 `res:hac:`**（不经过目标夹取）。

离线模型推演（非链上实测）：往返 swap 灌满 res 需要约 **942 次往返 / 93.5 HAC 手续费**（有 LP 时）。

**影响**：合约 B 在真实部署初期拿不到分红，除非 res 被清算推高。

**症状**：keeper 每轮崩溃在 `bytes.fromhex()`。

**验证**：修复后 7 组 24 键全部正确解析，实跑 `rent_keys` **7/7 批成功**。

## 🔧 2026-11-17：索引器地址监视修复（账本反复过期的真正根因）

### 现象

测试链账本**连续 4 次**在 2.8 小时后过期，池子、钻石、due 全部归零。
每次都重启 keeper，但下次照样过期。

### 根因：两个叠加的索引器 bug

**bug 1：`scan()` 只认 `kind=44`**

```python
if a.get("kind") != 44:
    continue
```

索引器只把**合约调用**记入地址台账。但：

| kind | 类型 | 是否触发合约钩子 | 原实现是否记账 |
|---|---|---|---|
| 44 | ContractMainCall | 是 | ✅ |
| **19** | TransferAssetFromTo | **是**（PermitAsset / PayableAsset） | ❌ **否** |
| **6** | TransferHacdFromTo | **是**（PermitHACD / PayableHACD） | ❌ **否** |

后果链：
```
股东用 asset-from-to 质押份额（kind=19）
  → 索引器不记账 → watched 一直是 0
    → keeper 拿不到地址键清单
      → due:<addr> / u:<addr> 这些键无人续租
        → PERIOD_NEW=100 期 = 10,000 块（1 块/秒 = 2.8 小时）后全部过期
          → 账本归零
```

**bug 2：`scan_many()` 的类型错误**

```python
found = sum(sum(per.values()) for (_h, _bh, per) in results)
```

`per` 是 `{addr: {fn: count}}` 嵌套结构，`sum(per.values())` 在累加 **dict** → `TypeError`。
这是既有 bug，**只要 scan 有任何命中就会崩**——而之前从没命中过，所以一直没暴露。

### 修复

| 文件 | 改动 |
|---|---|
| `hacds_indexer.py` `scan()` | 新增 kind=19 / kind=6 分支，按 `from`/`to` 是否为本合约记账 |
| 同上 | 新增 `_contract_set()`，`--contract` 支持逗号分隔多地址（A,B 同时监视） |
| `scan_many()` | 修正求和写法：`sum(cnt for fns in per.values() for cnt in fns.values())` |

### 验证

```
回溯扫描 5,001 块 → 命中 34 次，台账地址 34 个
索引器 /health → watched: 34（原为 0）
索引器 /rent_batches → 返回 klen=23 的地址键（u:<addr>）
keeper run --include-addr-keys → 160 批 / 160 键，成功 160 / 失败 0
```

**这是 H-2「续租闭环」在真实环境下的第一次真正成立。**之前所有「keeper 在跑所以没问题」的判断都是错的——keeper 拿不到地址键清单，等于没跑。

### 教训

`--include-addr-keys` 依赖索引器的活跃地址台账；台账依赖扫链识别合约相关交易；扫链识别的 kind 清单不完整 → 整条链断掉，但**每一环单独看都「正常」**。

### 关于 `get_claimable` 的语义

实测发现 claim 后 `get_claimable` 仍返回原值，一度以为是 bug。核实源码后确认**语义正确**：

```
get_claimable(who) = due(who) + 未结算增量
```

claim 把增量结算进 `due` 并推进 chk，所以 `due` 增大、增量为 0 → 总额不变。
它是「**已结算但尚未提现的总额**」，不是「距上次查询新增多少」。

提现需要另发 `TransferHacFromTo(B → 自己)`，由 `PermitHAC` 扣减 `due`。
