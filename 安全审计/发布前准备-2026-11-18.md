## 二、部署顺序（必须严格按此执行）

```
① AssetCreate serial 3000（hacds，5,963,298,700,000,000，decimal 0）
② AssetCreate serial 3001（股权，10,000，decimal 0）
③ 部署合约 A（nonce 2）   ← 必须先，B 的 link 校验要求 A 存在
④ 部署合约 B（nonce 3）
⑤ 立即启动 keeper（见第四节）
⑥ 首注建池 + topup_keys 补满键租期
```

**为什么 A 先 B 后**：B 的 `library [ ahac: … ]` 在部署时经
`check_link_contracts_exist()` 强制校验，A 不在链上就整笔回滚。

## 三、⚠ 部署前必须确认的三件事

### 3.1 部署者私钥可用

两个合约的地址都由「部署者 + nonce」推导。部署者必须是
`15fv6cNEapTNqYhigMPr38pC1XRKn3Wh5q`，否则地址全错。

**这个私钥在用户手上，我无法访问。**

### 3.2 `TREASURY → 合约 B` 的安全前提

审计 + 测试链实测都确认了这条攻击面：

```
PermitHAC 的 TREASURY 分支只校验 cp == TREASURY，不校验调用者身份
→ 任何人都能发 hac-from-to A B 清扫
→ 如果 B 的 PayableHAC 按 tx_main_addr() 记账，钱就进了清扫者兜里
```

**B 的设计规避了这一点**：`PayableHAC` 只用全局 `rpu:share` 累加器，
完全不碰 `tx_main_addr()`。测试链已验证第三方清扫无收益。

**这是 A 的 TREASURY 能指向 B 的唯一前提，不可更改 B 的记账方式。**

### 3.3 部署费余额

两笔共需 **20.16 HAC** + 两笔 AssetCreate 的手续费。
部署者地址需确认有足够余额（gas_max=99 时每笔预扣约 0.56 HAC）。

## 四、keeper 配置（部署后立即执行）

### 4.1 已修改的正式脚本

`install-services.ps1` 已改为 **daemon 自循环**：

| 项 | 值 |
|---|---|
| 模式 | `daemon`（进程内循环，不再依赖计划任务驱动） |
| 间隔 | `--interval 1800`（30 分钟） |
| 周期 | `--period 3000`（合约硬上限，≈3.5 天窗口） |
| 地址键 | `--include-addr-keys`（**原脚本缺这个，是账本反复过期的根因**） |
| 健康上报 | `--health keeper_health.json` |
| 失败处理 | 连续 5 轮失败退出 → 计划任务 RestartOnFailure 重拉 |

### 4.2 索引器配置

已改为**显式传 `--contract`**（原靠默认值兜底）。

⚠ **部署 B 之后必须把 B 的地址加进索引器的 `--contract` 列表**，格式 `A,B`。
否则 B 的转账不被记账 → B 的地址键无人续租 → 3.5 天后账本过期。

**这是测试链反复踩的坑**，务必执行。

## 六、部署后立即要做的事

| # | 事项 | 原因 |
|---|---|---|
| 1 | `topup_keys` 补满 A 的 24 个聚合键 | 新键只租 100 期（10,000 块 ≈ 2.8 小时@1秒/块，主网 5 分钟/块则 34.7 天） |

| 4 | 首注建池（≥1,000 HAC + ≥100 亿 hacds） | 参考价初始化门槛 |
| 5 | 验证 `/keeper_health` 返回 `ok` | 确认闭环生效 |

## 七、主网与测试网的差异（必须注意）

| 项 | 测试网 | 主网 |
|---|---|---|
| 出块间隔 | 1 秒 | **300 秒（5 分钟）** |
| `PERIOD_NEW=100` 期对应 | 10,000 块 ≈ **2.8 小时** | 10,000 块 ≈ **34.7 天** |
| `period=3000` 对应 | 300,000 块 ≈ 3.5 天 | 300,000 块 ≈ **1,042 天** |

**好消息**：主网出块慢，同样 10,000 块是 34.7 天而不是 2.8 小时，
账本过期的压力小得多。但**仍必须跑 keeper**。
