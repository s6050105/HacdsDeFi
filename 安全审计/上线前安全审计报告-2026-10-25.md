## 1. 执行摘要

**结论：当前代码不满足上线条件。**

发现 **4 项阻断级（Blocker）**，其中 3 项是**功能性瘫痪**（上线即坏），1 项是**上线即裸奔**。另有 5 项 High 级缺陷，均可在真实使用中造成资产损失或账本永久损坏。

### 1.1 四项阻断级问题

| 编号 | 模块 | 问题 | 后果 |
|---|---|---|---|
| **A-1** | Android | 时间戳注入位置错位一格，`fixed[2]` 应为 `fixed[1]` | **Android 端所有交易构造失败**（合约地址被时间戳覆盖 → 引擎 panic） |
| **B-1** | 官网 | `displayToAtoms` 按 decimal=8 换算，但 #3000 是 decimal=0 | **用户输入的金额被放大 1 亿倍** |
| **C-1** | 索引器 | `--read-only` 默认关闭、`--host` 默认 `0.0.0.0`，且 `.service` 未传参 | 按现有文档部署 **= 写接口公开无鉴权**（2026-10-22 的加固被回归） |
| **D-1** | 三端 + 引擎 | #3000 删除了证书，但**引擎、PC 钱包、Android、官网全部仍强依赖 126B 证书流**；预言机服务在 #3000 下已无存在意义 | **HACD 存入/赎回功能三端全挂**；且 PC/Android 会去请求一个已下线的服务 |

### 1.2 本轮最需要先决的问题

**A-1 是硬阻断，必须先修** —— 它不是"风险"，而是"功能不存在"：

```
Android buildOp → args = [main, "0", contract, fn, params]
          TxBuilder → argv = [exe, "call", main, "0", ts, fn, params]
                                    ↑            ↑
                              引擎 a[3]=ts   a[4]=contract  ← 被覆盖成时间戳

引擎 txbuild.rs:526  Address::from_readable(&a[4]).expect("contract address")
                     → panic: invalid address
```

同时 `MODES_WITH_TS` 漏了 `combo`，而 PC 端同源集合里有。**这是 2026-10-25 当天引入的回归**（`TxBuilder.kt` mtime 14:00，`main.js` 14:09，两端同时改但 Android 改错）。

**B-1 是资金级** —— `displayToAtoms` 用 `×1e8` 的旧 #2000 口径处理 decimal=0 的 #3000：

```
用户输入 100 hacds  →  上链 10,000,000,000 atoms（100 亿）
```

用户以为自己转了 100 个，实际发出 100 亿个。且 AMM 入池、加抵押、赎回取回全部走这条路径。

### 1.3 正面确认（经核实为真）

- **私钥三条线都做对了**：PC/Android 私钥均不落盘明文、不进渲染层、不进 WebView；子进程传的是**文件路径或内存覆盖**，从不出现在 argv。
- **keystore 加密正确**：scrypt N=2^15 / AES-256-GCM / 固定 AAD，PC↔Android 格式互通，篡改会被认证失败拒绝。
- **Electron 隔离到位**：`contextIsolation:true` + `nodeIntegration:false` + `sandbox:true` + 严格 CSP（无 `unsafe-inline`）。
- **合约不再有铸币权旁路**：#3000 删除预言机与证书后，HACD 存入改为链上读基因自算分，A-1（旧报告的 Critical）在架构上**已被消除**。
- **合约整数安全**：`mul_div` 走 256 位宽乘、`total_sub` 有饱和兜底、u128 回绕点均已加前置校验。
- **服务端零第三方依赖**：Python 纯标准库，无 `shell=True`/`eval`/`pickle`，命令注入面为零。

## 2. 阻断级发现（Blocker）

### A-1 【Blocker·功能瘫痪】Android 时间戳注入位置错位，全部交易构造失败

**位置**：`android-app/app/src/main/java/com/hacds/defi/engine/TxBuilder.kt:77-81`

```kotlin
val effective = if (mode in MODES_WITH_TS && args.size >= 3) {
    val fixed = args.toMutableList()
    fixed[2] = ts ?: nextTs()      // ← 应为 fixed[1]
```

**证据链**：

1. 调用方构造的 args **不含 mode**：`AppViewModel.kt:238` → `listOf(main, "0", c.contract, fnName, params)`
2. `build()` 把 mode 拼在 args 前面：`argv = ["hacds_txbuild", mode] + args`
3. 引擎侧按 `a[1]=mode, a[2]=main, a[3]=ts, a[4]=...` 取值：`txbuild.rs:420,478,480,526`

于是 `argv[3] = args[2] = contract` 被改成时间戳，而真正的 ts 占位 `args[1]="0"` 原样保留：

```
input : ['hacds_txbuild','call','MAIN','0','T1A8kae…','swap_hac_to_ds','100']
output: ['hacds_txbuild','call','MAIN','0','1792469415','swap_hac_to_ds','100']
                                  a[3]=0  a[4]=时间戳 ← 期望是合约地址
```

引擎 `txbuild.rs:526` 对 `a[4]` 调 `Address::from_readable(...).expect("contract address")` → **panic**。`transfer` 模式同理：`a[4]` 应是子形式 `hac-to`，变成时间戳后走 `other => panic!("unknown transfer sub-form")`（`:711`）。

**影响**：`call` / `transfer` / `combo` / `hacd` / `redeem-hacd` 全部无法构造交易。**Android 端等于完全不可用**（只能查询、不能操作）。

**次生问题**：
- `MODES_WITH_TS` 缺少 `combo`（对比 `main.js:113-114` 的 `TX_MODES_WITH_TS` 含 `'combo'`）
- `nextTs()` 用 `maxOf(now, prev+1)`，同秒第二笔会产出**未来时间戳**；而 `main.js:88-92` 的注释明确写"超前时间戳会被节点拒绝"。两端策略相反。

**修复**：

```kotlin
fixed[1] = ts ?: nextTs()
```
```kotlin
private val MODES_WITH_TS = setOf(
    "asset", "deploy", "call", "hacd", "redeem-hacd",
    "combo", "combined", "transfer", "redemption",   // ← 补 combo
)
```

`nextTs()` 改为与 PC 一致的"等待时钟进入下一秒"，不要产生未来时间戳。

**必须先验证再上线**：修完后跑一次真实构建，断言 `argv[4]` 是合约地址、`argv[3]` 是当前秒。

### B-1 【Blocker·资金级】官网金额换算沿用 decimal=8 口径，金额放大 1 亿倍

**位置**：`hacds.com/assets/js/txbuild.js:163-180`

```js
/** atoms（hacds 1e8 精度）→ 显示值 */
function atomsToDisplay(a) {
  const i = v / 100000000n; ...        // ÷1e8
}
/** 显示值 → atoms */
function displayToAtoms(s) {
  return (BigInt(i || '0') * 100000000n + BigInt(frac)).toString();   // ×1e8
}
```

**问题**：#3000 的 hacds 是 **decimal=0，1 atom = 1 hacds**（`发行参数-正式.md:§2`、合约 `HacdsDeFi3000.fitsh:181-186`）。这里仍按 #2000 的 decimal=8 做 ÷1e8 / ×1e8。

**实测放大倍数**：

| 用户输入 | 上链参数 | 实际含义 |
|---|---|---|
| `100` | `10,000,000,000` | **100 亿** hacds |
| `1` | `100,000,000` | 1 亿 hacds |
| `100000000` | `10,000,000,000,000,000` | 超总供应，直接失败 |

**受影响的操作**（`app.js` 逐条确认）：

| 操作 | 行 | 后果 |
|---|---|---|
| `swapDsToHac` | `:299` | 卖出量 ×1e8 → 池子被瞬间抽干式的滑点，或 `return 11`（due 不足） |
| `addLiquidity` hacds 侧 | `:334` | 入池量 ×1e8 |
| `removeLiquidity` minDsOut | `:358` | 滑点保护失效（设成天文数字 → 永远回滚） |
| `addCollateral` | `:425` | 抵押量 ×1e8 |
| 显示 `balDs` / `myColl` | `:167,199` | 显示值缩为 1/1e8（用户看到 `0.00000001`） |
| 池子 `pDs` | `:173` | 同上 |

同时 `swapHacToDs` 的 `minOut`（`:295`）也走 `displayToAtoms`，等于把滑点下限设成 1 亿倍，**交易必然回滚**。

**注意与 PC 端不一致**：PC 钱包 `renderer/app.js:98-101` 的 `rawHacds()` 是**原值直显 + `atoms`** 后缀，注释明确写"#3000 decimal=0，atoms 原值就是个，不需要 ÷1e8"（`:74-75`）。Android `Units.kt:13,22` 也是 1:1。**只有官网是旧口径。**

**修复**：官网删除两个换算函数的 ÷/×1e8，改为恒等（或直接内联），并把注释里的"1e8 精度"改为"decimal=0"。修完用 `发行参数-正式.md` 的三个用例自测：`1 分 → 100,000,000`、`3 分 → 300,000,000`。

### C-1 【Blocker·上线即裸奔】索引器写接口默认开放，加固被回归

**位置**：
- `hacds_exchange/indexer/hacds_indexer.py:639-640`（`--host` 默认 `0.0.0.0`）
- 同文件 `:683` 附近 `--read-only` 设为 `action="store_true"`（默认关）
- `hacds_exchange/indexer/hacds_indexer.service:9`（`ExecStart` 未传 `--read-only`）

```ini
ExecStart=/usr/bin/python3 /opt/hacds-indexer/hacds_indexer.py serve \
  --node http://127.0.0.1:8082 --port 8124 --interval 60 --window 500 --workers 4
```

**问题**：`安全审计/整改/8124-写接口加固说明.md` 的设计是「默认只听 `127.0.0.1`，服务器必须显式 `--host 0.0.0.0` 且同时传 `--read-only`」，文档原文还专门警告"若用 systemd，记得把 `--read-only` 加进 ExecStart"。**当前代码与单元文件两者都退回了加固前状态。**

按现有文件部署的结果：`0.0.0.0:8124` 上 `/sync`、`/watch/add`、`/watch/remove` 全部可用，**无任何鉴权**。

**影响**：
1. `/watch/remove?address=<借款人>` → 把真实借款人从清算台移除 → 无人清算 → 坏账；
2. `/sync` → 每次触发 4 线程并发扫链 → 打本地节点（放大器）；
3. 与 M-4（CORS `*`）叠加 → 任意网页可跨站发起，无需预检。

**修复（三处一起改）**：

```python
ap.add_argument("--host", default="127.0.0.1", ...)
ap.add_argument("--read-only", action="store_true", default=True, ...)
ap.add_argument("--allow-write", dest="read_only", action="store_false", ...)
```
```ini
ExecStart=... serve --host 0.0.0.0 --read-only ...
```
并去掉 `Access-Control-Allow-Origin: *`（改为 Origin 白名单，参考 `hacds.com/worker/index.js:corsHeaders`）。

### D-1 【Blocker·跨端功能瘫痪】#3000 删除证书，但引擎与三端仍强依赖 126B 证书流

**问题链条**：

1. 合约侧 `PayableHACD` / `PermitHACD`（`HacdsDeFi3000.fitsh:1342-1350, 1432-1440`）已**完全不读证书**：`check_hacd_wire` → `score_of(name)` → 链上读基因自算分。全文 `verify_cert` / `tx_message` 仅剩 2 处，都在注释里。

2. Rust 引擎仍强制要求证书文件：

```rust
// testkit/src/txbuild.rs:545-560  (hacd 模式)
let cert_path = a.get(6).expect("...<certfile>");
assert_eq!(cert.len(), names.length() * 126, "cert stream must be ...");

// :587-590  (redeem-hacd 模式)
let cert_path = a.get(7).expect("...<certfile>");
let cert = read_cert_stream(cert_path, names.length());
push_cert_actions(&mut tx, &cert);     // ← 强制把证书塞进 Message/Blob

// :206-215  (combo 的 hacd-to / hacd-from-to)
let cert_path = s("cert").unwrap_or_else(|| panic!("action[{idx}].cert missing"));
```

3. 三端都在**先向预言机取证书再传给引擎**：

| 端 | 位置 | 行为 |
|---|---|---|
| PC | `main.js:521-535, 666-680, 750-773` | 逐颗 `GET {oracle}/cert?name=X`，拼 126B 流写临时文件 |
| Android | `AppViewModel.kt:388, 391` | 传 `certFile.absolutePath` |
| 官网 | `txbuild.js:131-138` | 调 `deposit_hacd` / `redeem_hacd` —— **这两个合约函数根本不存在**（合约里是抽象钩子 `PayableHACD`/`PermitHACD`，由转账动作触发） |

**后果**：

- **HACD → hacds 的存入、hacds → HACD 的赎回，在 PC / Android / 官网三端全部无法工作**。而这是协议的核心功能（README 首句："存入 HACD 铸造 hacds，随时赎回"）。
- 预言机服务已随 #2000 停用（README："预言机关闭"），PC/Android 会去请求一个不存在的服务 → 用户看到的是网络错误而非"功能未适配"。
- 即便预言机仍活着，其签出的证书在 #3000 合约里**没有任何作用**（合约不读），只是白白占 126B × n 的 tx 体积与 gas。

**修复（两选一，需你决策）**：

**方案 A（改引擎，推荐）**：给 `txbuild` 增加无证书路径。因为 `TransferHacdTo` / `TransferHacdFromTo` 本身不需要证书，只需不带 `push_cert_actions`：

```
hacd        <main> <ts> <contract> <NAMES>            # certfile 变可选
redeem-hacd <main> <ts> <contract> <to> <NAMES>       # certfile 变可选
combo spec: { "type":"hacd-to", "to":…, "names":… }   # cert 可选
```

三端相应删除取证书的代码分支与 `oracle` 配置项。**这是正确的终态**，也顺带把预言机从发布包里拿掉。

**方案 B（临时绕过，不推荐）**：让预言机继续跑并签出"格式合法但内容无意义"的 126B 流喂给引擎。可行但荒谬 —— 保留一个只为了凑字节的服务，且仍留单点。

## 3. High 级发现

### H-1 【High】索引器 `rent_batches` 静默截断，第 51 个地址起永远漏续租

**位置**：`hacds_indexer.py:451-453`

```python
n = len(raw) // klen
if n > 50:
    n = 50              # ← 把总数截成 50，而不是分页
for i in range(0, n, max_keys):
```

**离线复现**（60 个合法地址，实测）：

```
真实键数 240（u:/ln:/ck:/bad: 各 60）
输出批数 15 批 × 10 = 150 条
丢失 90 条
```

**后果**：活跃地址超过 50 个后，第 51 个起的地址账本键**永远不进续租清单**。键过期 → `storage_load` abort `StorageNotActive(108)` → 该用户存款/取款/swap/赎回/还款**全部整笔回滚**，合约无管理员、无人能救。

**修复**：删除截断，改真分页（`offset` + `next_cursor`），或返回 `truncated:true` + `total_all` 让 keeper 报错停下。

### H-2 【High】keeper 对 `klen=24` 键型的 storage 容量算错，续租整笔 OutOfGas

**位置**：`hacds_exchange/indexer/hacds_keeper.py:84-92`

```python
def _value_len(klen, blob_hex):
    if klen == 23:
        prefix = bytes.fromhex(blob_hex)[:2]
        if prefix == b"ck": return 64
        return 48
    return 16
```

**实测键长**：

```
u:   → 23 字节（值 48）
ln:  → 24 字节（值 48）   ← 落到 return 16
ck:  → 24 字节（值 64）   ← 落到 return 16
bad: → 25 字节（值 16）
```

`klen==24` 一律返回 16，`prefix == b"ck"` 分支**永不可达**；第 78 行的 `VALUE_LEN_BY_KLEN` 定义后从未被引用（死表，且同样把 `ck:` 记成 23）。

**后果**：扩容被低估 3~4 倍。真实成本：

```
ln: ×10 键 = (48+20)×300×10 = 204,000 > 单桶上限 111,911  → OutOfGas
ck: ×10 键 = (64+20)×300×10 = 252,000 > 111,911            → OutOfGas
```

即**每笔含 >5 个 `ln:` 或 >4 个 `ck:` 的续租交易必然整笔回滚**，而 `ln:`/`ck:` 正是打包后的主力键。配合 H-1，存量借款人会在 34~104 天后账面"归零"。

**修复**：按 24 字节前缀分支（`b"ln"`→48、`b"ck"`→64），正确上限 `u:/ln:→5`、`ck:→4`、`bad:→10`。

### H-3 【High】台账状态文件损坏时静默清零

**位置**：`hacds_indexer.py:125-133`

```python
try:
    with open(self.state_file, ...) as f:
        j = json.load(f)
    self.watch = j.get("watch", {}) or {}
    self.last_scanned = int(j.get("lastScanned", 0) or 0)
except Exception:
    pass          # ← 任何解析失败都静默吞掉
```

**后果**：磁盘满（日志无轮转，只 append）、进程被 kill 在写入中、手工编辑出错 → `watch={}`、`last_scanned=0` → 首次 sync 只回溯 500 块 → **历史借款人集体从台账消失，日志一句不提**。清算台对老仓位完全失明。

**同源问题**：`save()` 用固定路径 `state_file + ".tmp"`，poller 线程与 HTTP `/sync` 可并发调用 → 互相截断 → 发布半截文件 → 又被上面的 `except: pass` 清空。

**修复**：区分"文件不存在"与"解析失败"，后者**拒绝启动**；`tmp` 用 `mkstemp` 唯一名；`sync()` 加锁（拿不到返回 busy）。

### H-4 【High】Electron 无导航拦截，渲染层被注入即可接管全部 IPC

**位置**：`wallet-app/main.js:1098-1116`（全文无 `will-navigate` / `setWindowOpenHandler`）

`contextIsolation` + `sandbox` 只隔离了 Node，**没有限制 preload 在哪个源上生效**。一旦主窗口被导航到远端页面，该页面继承完整 `window.api`：`walletExportKey` / `buildTx` / `combo` / `broadcast` / `walletDelete`。

**放大因素**：同一份渲染层有 47 处 `innerHTML`，其中多处直接拼远端字段（`app.js:1946` 的 `i.name`/`i.score`、`:227-233` 的 `c.name`、`:1017-1030` 的 `it.address`、`:1957-1975` 的 `dims.*`），数据来自明文 HTTP 的节点 `/query/diamond` 与索引器 `/snapshot`。CSP 挡住内联脚本，但挡不住 `<meta http-equiv="refresh" content="0;url=http://attacker/">`。

**后果**：明文链路上的 MITM 可注入 meta refresh → 导航到攻击者页面 → 该页面调用 `buildTx` + `broadcast` 转走全部资产（**不需要私钥导出**）。

**修复**（改动极小、收益最大）：

```js
win.webContents.on('will-navigate', (e, url) => {
  if (!url.startsWith('file://')) e.preventDefault();
});
win.webContents.setWindowOpenHandler(() => ({ action: 'deny' }));
```

同时给远端字段统一补 `esc()`（`esc()` 已存在，只是覆盖不全）。
