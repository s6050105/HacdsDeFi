### 0.2 单位与换算（**唯一口径**）

| 量 | 链上单位 | 界面单位 | 换算 |
|---|---|---|---|
| HAC 侧（`bal:hac` / `amm:hac` / `loan:debt` / `tre:hac`） | zhu | **HAC** | 1 HAC = 1e8 zhu（显示 ÷1e8，输入 ×1e8） |
| hacds 侧（`due` / `amm:ds` / `loan:coll` / `#2000 amount`） | atoms | **atoms（raw，不换算）** | — |
| LP 份额 `lpt` | 无定标（`√(hac×ds)`） | 原值 | 不除以任何数 |
| `pool_price` | `amm:hac × 1e8 / amm:ds` | `HAC/hacds` | ÷1e8 |

**hacds 的统一口径**（D44/D55）：

- hacds **全端用 atoms**：余额、池子、抵押、输入框、报价，看到的都是 atoms，
  与浏览器、交易所接口同一口径。
- **不做 ÷1e8 转换**。要「个数」自己除 1e8（`7000000000` atoms = 70 个 hacds），
  但**不要把这个读数填进输入框** —— 用户看见 70 就填 70，实际只转了 70 atoms，差 1e8 倍。
- 输入框标签必须写明 `atoms`，并在默认值上给出量级参考（如 `100000000` = 1 个 hacds）。

### 0.3 协议硬上限（Hacash VM）

vm 三桶**各自独立**、与总预算 `gas_max` **无关**（`hacash-params/src/lib.rs`，`decode_gas_budget` 表）：

| 桶 | 参数（字节） | 主网上限 |
|---|---|---|
| compute | `compute_limit_byte = 72` | **18,009** |
| resource | `resource_limit_byte = 56` | **6,100** |
| storage | `storage_limit_byte = 99` | **111,911** |
| 总预算 | `tx_gas_budget_cap_byte = 99` | 111,911 |

- 错误形态：`OutOfGas(31): resource gas limit exceeded: used 6101 > limit 6100`
- **单桶超限时提高 `gas_max` / 手续费完全无效**；只能拆笔或减少新键。
- **单笔「存入兑换 hacds」最多 1 颗 HACD**：`PayableHACD` 对每颗调 `verify_cert`（含链上重算评分），实测约 **3,000 resource/颗**，2 颗即 6,101 > 6,100（D40/D41）。
- 这些是**共识参数**，改动等于分叉。

### 0.4 借贷口径（合约 `HacdsDeFi.fitsh`）

| 项 | 定义 |
|---|---|
| 抵押折 HAC 价值 | `coll_to_hac(coll) = coll × amm:hac / amm:ds`（zhu） |
| 放行条件 | `(debt + hac_amt) × COLL_RATIO(2) ≤ coll_hac`，否则 `return 40` |
| **可借上限** | `coll_hac / 2 − debt` |
| **需抵押** | `(debt + 借款) × 2 × amm:ds / amm:hac` |
| 抵押率 | `coll_hac × 100 / debt`（`loan_status`；`debt = 0` → 哨兵 `999`） |
| **可清算** ⟺ | `debt > 0 && 0 < health < 200` |
| `loan_status` 返回值 | `0` = 无借贷无抵押；`999` = 有抵押无债务（安全）；其它 = 抵押率 ×100 |

> ⚠ **200 是「清算线」，不是「50% 抵押率」**：可借上限 = 抵押价值 ÷ 2 = **50% 抵押率**；
> 「抵押率跌破 200」与「债务超过抵押价值的一半」是**同一约束的两种说法**，不要当成两个阈值。

## 1. 定位与目标

**是什么**：Windows 桌面程序（Electron），让用户可视化完成 HacdsDeFi 合约的全部操作，并内置钱包（创建/导入/加密保管）。

**目标用户**：

| 类型 | 主要用途 |
|---|---|
| 普通持币人 | 拿 HACD 换 hacds、参与 AMM、借贷 |
| 项目方/运营 | **管理员操作**（专属界面）、续租 |

**非目标（不做）**：全节点、多签/硬件钱包、多节点广播、代码签名、自动更新。（移动端另见《Android 设计文档》）

## 2. 系统架构

```
┌─────────────────────────── Electron 应用 ───────────────────────────┐
│ 渲染进程 (renderer/)          │ 主进程 (main.js)                      │
│  · index.html/style.css/app.js│  · IPC 白名单 (preload.js 桥接)       │
│  · 表单/预览/广播 UI          │  · 钱包 (keystore.js)                 │
│  · 只发 IPC，无 Node 权限      │  · 手续费估算 (fee.js)                │
│                               │  · spawn hacds_txbuild.exe 构建+签名  │
│                               │  · HTTP 调节点 / 预言机               │
└───────────────┬───────────────────────────┬──────────────────────────┘
                │ spawn(env 注入私钥)         │ HTTP
                ▼                             ▼
      hacds_txbuild.exe              全节点 API  ┐
      (构建+本地签名，随包)           预言机      ┘ 均在服务器
```

**关键决策**：交易构建与签名**不重写**，复用已验证的 `hacds_txbuild.exe`（GUI 只负责界面与调用）——降低共识层出错风险。

**安全边界**：
- 渲染进程 `contextIsolation: true` + `nodeIntegration: false`，仅通过 `preload.js` 白名单调用主进程
- 私钥只在**主进程内存**解密，构建时以环境变量 `HACDS_SIGN_KEY_HEX` 注入子进程 → **全程不落盘**
- 无网络上报、无中心服务器

#### 4.2.3 预期 hacds 本地计算 —— 可行性确认 ✅（D13）

**你的问题**：预期 hacds 能否**直接读全节点基因**计算？

**结论：能，且完全不需要调预言机。**

**原理链**（已逐段核实）：
```
/query/diamond?name=X     →  life_gene(32B) + number
        │
        ├─ visual_gene_hex(name, life_gene)   ← 纯函数，本地派生（20 hex）
        │
        └─ analyse(name, number, visual_gene) ← 纯函数，5 维评分
                    ↓
              score（1~多）
                    ↓
        预期 hacds = Σ score × 10⁸
```

- 预言机的 `analyse()` **只依赖 name + number + visual_gene**，三个都是纯输入
- `visual_gene` 可由 `life_gene` 本地派生（`calculate_diamond_visual_gene`，算法在 `mint-core/src/exec/diamond.rs` 与预言机 `visual_gene_hex()` 中一致）
- 评分逻辑**零外部依赖**（仅算术 + 4 张常量表 + 字符串处理）
- Node 内置 `crypto` 有 `sha3-256`；评分部分连 sha3 都不需要（只有 `visual_gene_hex` 的派生用到）

**移植方案**：把预言机的评分段（约 350 行 Python：`RULE_SCORES` 表 + `get_shapes/get_styles/get_color/get_nameliteral/get_numberliteral/_clean_score/analyse` + `visual_gene_hex`）**逐行移植为 JS**（`diamond-score.js`），并用**预言机做交叉验证**（same input → same score）。

**优势**：
- 无需逐颗调预言机（112 颗省去 112 次 HTTP）
- 离线可用；无信任问题（算法确定性，可与预言机结果比对）
- 与证书无关——**只是"预期值"展示**；真正上链兑换时仍由合约链上重算，用户仍需预言机出的证书

> 注意区分：**本地算的是"预期积分"（展示用）**；**上链兑换仍需预言机证书**（合约验证的是预言机签名 + 链上重算）。两者算法相同，结果必然一致。

#### 4.5.1 AMM 交易面板：实时报价 + 池状态（D18，本期做）

**需求**：AMM 页直接显示"投入 → 预期得到"的实时报价，并在旁边显示池子总量（HAC / hacds），类似 DEX 界面。

**✅ 可行性确认：完全可在本地计算，无需链上调用。**

合约 `amm_swap` 的公式（已核实源码）：
```
恒定乘积：x × y = k，对**输入腿**收取 fee_bps（默认 50 = 0.5%）
HAC → hacds:  net_in = in × (1 − fee) ;  out = pool_ds × net_in / (pool_hac + net_in)
hacds → HAC:  net_in = in × (1 − fee) ;  out = pool_hac × net_in / (pool_ds + net_in)
```
- 池储备来自只读查询 `amm_reserves()`（`amm:hac`）与 `amm_reserve_ds()`（`amm:ds`）
- 费率来自 `pool_price()` 间接体现，实际 `fee_bps` 在 `cfg:fee`（**注意**：`cfg:fee` 是 status 键，标准只读接口未直接暴露；用 `pool_price()` 反推或直接按默认 0.5% 展示并标注）

**面板设计**：
```
┌─ AMM 兑换 ──────────────────────────────────────────────┐
│  方向  [HAC → hacds ▾]                                   │
│  投入  [ 1000000        ]  HAC 积分                      │
│                                                            │
│  ┌─ 预期得到 ──────────────┐  ┌─ 池状态(实时) ──────────┐ │
│  │ 约 995,024 hacds        │  │ 池 HAC    12,345.6789   │ │
│  │ 价格  1 HAC = 0.995 ds  │  │ 池 hacds  12,345.6789   │ │
│  │ 费率  0.5%              │  │ 池价  1.0000 HAC/hacds  │ │
│  │ 滑点  ~0.01%            │  │ LP 总量  3,512.34       │ │
│  └─────────────────────────┘  └─────────────────────────┘ │
│  [生成交易]                                                │
└────────────────────────────────────────────────────────────┘
```
- **输入即算**（本地，无延迟）：改投入额 → 即时更新预期输出/价格/滑点
- 池状态每次进入页面刷新，另设"刷新"按钮
- 也可把**储备值直接显示**在面板旁（D18 要求）

### 4.6 HACD 赎回（D9，本期做 —— 形态验证）

**链上机制**（已核实合约 `PermitHACD` 钩子）：
```
动作1  Message/Blob（所选钻石的证书流）
动作2  TransferHacdFromTo(from=合约, to=我的地址, diamonds=[...])   → PermitHACD 钩子
```
PermitHACD 钩子：① 证书验签 + 链上重算评分；② 校验 `due:<我> ≥ Σ score×10⁸`，**不足时合约自动经 AMM 用 HAC 积分补足差额**；③ 扣 `due` 与 `tot:ds`（配额销毁）；④ HACD 所有权移动完成交割。

**App 侧实现**：
- 复用 `hacd` 模式的证书取用逻辑（预言机 `/cert`）
- 参数：钻石名列表 + 目标地址（默认当前账户）
- 交易形态：`transfer hacd-from-to <main> <ts> <合约> <我> <names> <certfile>`

**本期限制（重要）**：
> 合约当前**没有 HACD 库存**（尚无用户存入过钻石），因此赎回**无法在链上真跑成功**。
> 本期只做**形态验证**：生成交易 → 节点 `/util/transaction/check` 解析正确（动作 kind 6 + 证书）。
> 待合约有库存后再补**链上实跑**验证。

### 4.7 手续费自动估算（D7，v0.1 已实现并实测）

**规则**：`纯度 = fee(u232) / billing_size(字节)`，节点准入要求 `纯度 ≥ min_purity`（当前 ≈ `6024000000`）。

**实现**：迭代构建（`fee.js` + `main.js::buildWithAutoFee`）——默认 `0.0002` 构建 → 读**已签名后**真实字节数 → 不足则按所需 fee 重建，通常 1~3 轮收敛。

> 迭代必要性：**提高 fee 会让字节数微增**（fee 编码变长），一次计算会低估。实测：`0.0002@424B → 0.00033204@427B → 0.00033439@427B`。

| 操作 | size | 最低 fee | 默认 0.0002 |
|---|---|---|---|
| `call lp_harvest` | 171 B | 0.000134 | ✔ |
| HACD 存入 ×1 | ~230 B | 0.000180 | ✔ |
| HACD 存入 ×2 | 427 B | 0.000334 | ✘ 自动上调 |
| deploy 合约 | ~10400 B | 0.00809 | ✘ 自动上调 |

界面显示`手续费 <值>（自动）`；高级选项留空=自动，填了=手动。费率每次构建实时读节点 `/query/fee/average`。

### 4.10 离线签名工作流（冷热分离）（D23，本期做）

**需求（已澄清）**：用户可在**离线钱包只创建交易体、不签名**；先验证交易体无误，再到**联网钱包签名并广播**。即经典的**冷热分离**（离线构建 + 在线广播，私钥永不触网）。

**✅ 可行性确认：已实测跑通。**

现成能力（`hacds_txbuild`）：
| 步骤 | 命令 | 输出 |
|---|---|---|

| **签名**（离线/冷端） | `txbuild sign <keyfile> <unsigned_hex>` | `signed_tx_hex`，`signed_check = OK` |

**实测**：无密钥构建 → 124B 未签名体 → `sign` 后 `verify_signature` 通过 ✅

**App 侧设计**：

```

│                                                          │

│                                                          │
│  【第 2 步 · 验证】（可选，需节点）                        │
│   [校验未签名体]  [翻译交易体]  ← 调节点 check/description │

│                                                          │

│   粘贴 unsigned_tx_hex   [选择钱包/私钥]  [签名]          │
│   → 输出 signed_tx_hex                                    │
│                                                          │
│  【第 4 步 · 广播】（联网机）                              │
│   粘贴 signed_tx_hex   [广播]                             │
└──────────────────────────────────────────────────────────┘
```

**要点**：
- **离线机可完全断网**：构建、签名都纯本地（`hacds_txbuild` 不联网）
- **未签名体的"验证"**：可调节点 `/util/transaction/check`（**这只是人工核对**，节点不接受未签名交易进 mempool，`submit` 会因签名缺失被拒）
- 传输载体：hex 文本复制 / 存文件 / **二维码**（大交易二维码不便，优先文件/文本）
- 签名前应核对：`sign_digest` 与 `unsigned_tx_hex` 是否来自同一笔（App 自动校验一致性）
- **私钥始终不触网**——这正是该流程的核心价值

**与 D24 原子交易的配合**：离线模式同样支持 combo 组合交易（先离线构建多动作体 → 验证 → 签名 → 广播）。

> 附：协议**无**"消息签名"类 action（消息签名需自建格式且链上无验证场景），故 **D23 最终定义为"离线签名工作流"**，不再做通用消息签名。

### 4.11 原子交易（D24，本期做）

**需求**：把多步操作合并成**一笔交易**，要么全成、要么全败。

**可行性确认**：
- 协议**一个交易最多 200 个 action**（`tx_actions_max = 200`），天然原子——任一 action 失败则整笔回滚
- 合约设计本就为此准备，如**存入 + 领取同笔**（设计文档 v4 §5.1）：
  ```
  动作1 Message(证书)  动作2 TransferHacdTo(合约,[钻石])  动作3 TransferAssetFromTo(合约→我,hacds,n)
  ```
  一笔完成"HACD 存入 + 立刻领取 hacds"

**实现方式**：给 `hacds_txbuild` 增加**组合模式**（如 `combo`），把多个子动作按序拼进同一 tx：
- 场景预设（常用组合）：
  | 组合 | 动作序列 |
  |---|---|
  | 存入+领取 | `Message/Blob(证书)` + `TransferHacdTo` + `TransferAssetFromTo` |
  | 充HAC+兑换 | `TransferHacTo` + `call swap_hac_to_ds` |
  | 兑换+领取 | `call swap_hac_to_ds` + `TransferAssetFromTo` |
- 通用：允许用户**自由增删/排序** action 再构建

**技术注意**：
- **不能在节点侧签名**：节点的 `/util/transaction/sign` 要求把**私钥经 HTTP 发过去**（`prikey` 参数），**违背本地签名原则，禁用**
- 正确路径：App 用 `hacds_txbuild` 的 combo 模式**本地拼装 + 本地签名**；节点只用来**翻译/校验/广播**
- 各子动作的字节数影响手续费 → 走 4.7 的**迭代自动估算**（组合后交易更大，会自动升 fee）

**本期范围**：先做**预设组合**（上表 3 种），自由编排留待后续。

#### 4.12.1 单位约定（实现细节）

**口径表见 §0.2**（唯一口径，不再重复）。此处只保留**代码约定与推导**。

**代码约定**（`renderer/app.js`）：
```js
const ATOMS_PER_UNIT = 1e8;
const atoms = n => n/1e8;   // atoms → 个数
const zhu   = n => n/1e8;   // zhu → HAC 个数（公式同，命名区分只为防错）
const share = n => n;       // LP 份额：原值，不换算
```

**核对过的链条（1 分 = 1 个 hacds）**：
- 合约 `SCORE_SCALE = 1e8`；`due += sc × 1e8`（atoms）
- 预言机 `hacds_amount = score × 1e8`（atoms）
- 发行 `supply = 59,632,987 × 1e8` atoms（= 59,632,987 个 hacds）
- ⇒ **score=10 → due/资产量 1,000,000,000 atoms → 显示 10 个 hacds**

> **踩过的坑**：曾把"预期 hacds"直接当个数用（未走 atoms 路径）；LP 份额曾误用 `atoms()`（÷1e8）显示——都是量纲错误。**新增字段显示时必须先查它的量纲。**

##### 关于「1 分 = 多少个 hacds」的口径（D38 定稿）

**已部署的链上参数（不可改）**：合约 `SCORE_SCALE = 1e8`、资产 `decimal = 8`、`supply = 5963298700000000`。

| 口径 | 结果 |
|---|---|
| **实际（decimal=8）** | `due = score × 1e8 atoms`；显示 **1 分 = 1 个 hacds** |
| 曾考虑（decimal=0） | 同样的 `supply` 数字会显示为 5.96e15 个 hacds，即 1 分 = 1e8 hacds |

**决定：维持现状（A）**。理由：
- decimal=8 已满足「HACD 可拆细交易」的目的（最小单位 1 atom = 1e-8 hacds）
- 改为 1e8 只让显示数字变大，无实际收益
- 链上已固化，改动需重新部署合约 + 重新发行，代价大

> 节点 API 返回的是 `amount`（原始最小单位）+ `decimal`，**由客户端按 decimal 换算显示**（`5963298700000000 / 10^8 = 59,632,987 hacds`）。

#### 4.13.2 单桶 gas 上限（D40–D41）—— 重要协议事实

**三桶上限见 §0.3**（唯一口径，不再重复）—— 要点：三桶各自独立、与 `gas_max` 无关，单桶超限时提高 `gas_max` 无效。

**实测（2026-10-21，真机主网）**：

| 场景 | resource 消耗 |
|---|---|
| 空调用（`lp_total()` / `amm_reserves()`） | ~206 |
| 单颗钻石评分（`quote_score`，与链上 `verify_cert` 同路径） | ~3,230（净 ~3,024） |
| **1 颗存入**（TransferHacdTo + Message 证书） | ✅ **广播成功**（tx `5380f6…09f1`） |
| **2 颗存入** | ❌ `resource gas limit exceeded: used 6101 > limit 6100` |

> 根因：`PayableHACD` 对**每颗**钻石调 `verify_cert` → `sha3` + `verify_signature` + **链上重算评分**（最重），约 3,000 resource/颗，与名字/基因无关。2 颗 ≈ 6,050 净 + ~51 开销 = **6,101**，超 1 点。

**结论（D41）**：单笔存入**最多 1 颗**；多颗**拆成多笔**；**原子交易不能绕过**（共享同一 gas 预算）。前端在 `names.length > 1` 时弹确认（D41），错误翻译给出指引（D42）。

#### 4.13.3 错误翻译（D42）

`contract-errors.js` 的 `NODE_ERRORS` 新增三条**单桶专用规则**，且**必须排在通用 `OutOfGas` 规则之前**（否则被 `/gas has run out|OutOfGas/i` 抢先匹配）：

| 匹配 | 文案 | 提示要点 |
|---|---|---|
| `resource gas limit exceeded` | resource gas 单桶上限超出（与 gas_max 无关） | 主网 6,100；常见于一次存入多颗 HACD；请拆笔；提高 gas_max/手续费无效 |
| `compute gas limit exceeded` | compute gas 单桶上限超出（与 gas_max 无关） | 主网 18,009；拆笔 |
| `storage gas limit exceeded` | storage gas 单桶上限超出（与 gas_max 无关） | 主网 111,911；减少新键或降租期 |

> 规则顺序即优先级（`translateNodeError` 顺序遍历、首个命中即返回）。

#### 4.13.4 批量转入 / 批量赎回（D43）

**是什么**：HACD 收藏页勾选多颗后，一键「批量存入兑换」或「批量赎回」，**自动拆成「每笔 1 颗」的独立交易并逐笔广播**。

| 入口 | 位置 |
|---|---|
| 勾选工具条 | 「批量存入兑换（n）」「批量赎回（n）」——未勾选时禁用 |
| 详情栏 | 单颗卡片下方的「批量存入兑换 / 批量赎回」（等价于对当前这颗执行一次） |

**实现**：`main.js::tx:redeemBatch`（IPC `tx:redeemBatch`，preload 暴露为 `api.redeemBatch`）

- `kind='in'` → `TransferHacdTo`（我的钻石 → 合约，记 `due` 配额）
- `kind='out'` → `TransferHacdFromTo`（合约 → 自己，扣 `due` 配额）
- 逐颗循环：向预言机取证书 → 写 126B 证书临时文件 → `txbuild hacd|redeem-hacd` 构建单颗 → **立即广播** → 记录 hash
- 每笔之间节流 120 ms，避免对节点瞬时并发过高
- 返回**逐颗结果**：`{ total, succeeded, failed, items:[{name, ok, hash|error, translated, hint}] }`
- 前端逐颗打印日志（`[i/n] NAME ✔ hash` / `✘ 原因`），完成后汇总成功/失败数；**全部成功才清空勾选**（避免误重复提交）

**关键结论（实测）**：
1. **必须拆笔**：单笔 resource 上限 6,100、每颗约 3,000 → 一笔只能 1 颗（见 4.13.2）。
2. **原子交易不能替代拆笔**：`combo` 合并多个存入动作仍在**同一笔**内，共享同一 gas 预算，照样超限。
3. **同 timestamp 可并行**：Hacash Type-3 **无 consensus nonce**，交易唯一性只由 `hash_with_fee` 决定（含 main + fee + timestamp + actions）。实测**同一时间戳**构建的 3 笔单颗交易 **hash 互不相同、全部广播成功**。因此 `txbuild` 传 `ts=0` 是安全且确定的（同参数 → 同 hex → 同 hash）。
4. **成功判据**：`submit/transaction` 返回 `ret:0` 仅代表**进入 mempool**，不代表已上链；最终以 `due` 配额 / 钻石归属变化为准。

> 实测记录见 **§7 已验证事实**（批量转入 3/3、单颗广播成功）。

**二次确认**：批量执行前弹窗明确告知「将自动拆成 N 笔、每笔 1 颗」并列出名称（`hacd.batchPlan`）。

**实现**：`app.js` 用**展示专用**格式化函数 `rawHacds()`：

```js
// 链上原始量（#2000 amount 原样），BigInt 防大数精度丢失
const rawHacds = (n) => { ... BigInt(String(n)).toLocaleString('en-US') ... };
```

- 用 **`BigInt`** 而非 `Number`：总供给量级 5.96e15 已在 `Number.MAX_SAFE_INTEGER`(9.007e15) 边缘，字符串化处理更稳。
- 副标题同步注明口径（`ov.onchainSub` / `ov.dueSub`），避免被误读为「个数」。
- 操作区的 `atoms()`（÷1e8）**现已成为死代码**，无调用点（已核实）。
- **未改动**：HAC 侧（`zhu` → HAC）、LP 份额（`share`）、价格、健康度。

**为什么不把输入框改成 ÷1e8**：改的话界面会出现两个口径，用户按「个数」的读数去填 atoms 框，少写一个零就是 1e8 倍资金误差。统一成 atoms，输入框标签写明单位，反而最不容易错。

**交易所对接口径**：`serial=2000` 的 `amount` = raw atoms；个数 = `amount / 1e8`。合约与链上数据无需改动。

#### 加流动性两侧联动（D62）

合约 `add_liquidity(hac_amt, ds_amt)` 的份额规则是 `share = min(lpttot×hac/ph, lpttot×ds/pd)`，
**两腿比例不匹配时取小的那侧算份额，多注的那侧白送进池子**。

所以加流动性卡做了两侧联动：改一侧，另一侧按池内比例自动配平（下取整）。
首注（池为空）没有比例可对齐，两侧都由用户定，份额 = `isqrt(hac_amt × ds_amt)`。

| 场景 | 界面行为 |
|---|---|
| 池内比例 | 显示「池内比例 X HAC ↔ Y atoms」 |
| 改 HAC 侧 | 自动填 `ds = hac_zhu × pd / ph` |
| 改 hacds 侧 | 自动填 `hac = ds × ph / pd` |
| 两腿不匹配（>1 单位） | 红字告警 + 给出配平值 |
| 首注 | 提示两侧自定，并预估份额 |

> 取整容差：下取整必然差 1 个单位，不算不匹配，不告警。

**顺带修的坑**：该卡原默认值 `hac_amt=1` / `ds_amt=100000000` 与池比例不符，
照默认提交会白送约 0.67 hacds。已把 `ds_amt` 默认改为 `0`（由联动填）。

---

> 补充事实（2026-10-21 实测）：用户钱包 #2000 = `7,000,000,000`（= 70 个 hacds）、合约持有 = `5,963,291,700,000,000`、总供给 = `5,963,298,700,000,000`。三者满足 `用户 + 合约 = 总供给`（用户持仓即合约已赎回出去的部分）。

### 4.15 sandboxcall 并发闸门 + 重试（D45）

**现象**：协议状态面板刷新之间**数值不一致** —— 同一组字段这次有值、下次变 `—`，且每次缺的不是同一个。

**根因**（实测定位）：节点对 VM 沙箱调用有**每 IP 并发上限**：

```rust
// base/src/api/limiter.rs
pub const DEFAULT_GLOBAL_CONCURRENCY: usize = 8;
pub const DEFAULT_PER_IP_CONCURRENCY: usize = 2;   // ← 每 IP 只允许 2 个并发
```

`protocol:overview` 用 `Promise.all` 一次性发 **14 个** sandboxcall → 超出的被立即拒绝（无排队）：
`{ret:1, err:"sandbox_per_ip_concurrency_exceeded"}`，而调用处 `.catch(() => null)` → 该字段渲染成 `—`。**被拒的是哪几个是竞态决定的** → 刷新间不一致。

**修法**：`main.js` 新增全局闸门，把**所有**沙箱查询串行化到并发 1，并对忙类错误做指数退避重试。

- **为什么并发=1 而不是 2**：并发 2 正好顶着节点上限，仍可能撞限；串行化则确定性成功，且沙箱查询都是毫秒级、面板刷新无感。
- **重试要判 body 层**：节点拒绝时是 **HTTP 200 + `{ret:1, err}`**，只看 HTTP 状态码抓不到。
- **统一入口**：新增 `sandboxGet()`，**7 处** sandboxcall 调用点全部改走它（协议总览 / 资产总览 / 管理员探测 / 通用查询 / 钱包批量余额）。
- 非沙箱请求（`/query/balance`、预言机 `/cert`）不占名额，不受影响。

**验证**：连跑 10 轮 14 字段 → **全部 0 个 null**（修改前随机 1~3 个）。

### 4.16 广播后延迟刷新（D46）

**现象**：官方浏览器已显示转账成功，但钱包「刷新资产」后余额**没变** —— 看起来像刷新失效。

**根因不是节点未同步**，而是**出块节奏**：

- 实测节点高度持续推进、peers=4、`block_target_seconds: 300`（与源码 `each_block_target_time: 300` 一致）→ **节点完全同步**。
- `submit/transaction` 返回 `ret:0` 只表示**进入内存池**；Hacash **5 分钟一个块**，要等下一个块才落链。广播后立刻刷新只能看到旧状态。

**修法**：广播成功后，除立即刷新（合约内 `due`/积分当笔即生效）外，**按出块节奏补刷**：
`15s / 45s / 90s / 180s / 320s`（最后一档跨过完整出块周期），并在日志中说明「交易已进内存池，等待打包」。

**给用户的结论**：余额「没刷新」通常是**等块**，不是同步问题、也不需要重启节点。

### 4.17 引擎模式自检（D48）

**现象**：批量赎回 100% 失败，报 `unknown mode redeem-hacd`。

**根因**：`wallet-app/bin/hacds_txbuild.exe` 是 **10-20 15:13** 的构建，比源码版（19:25）**早 4 小时** —— 那时 `redeem-hacd` 模式尚未加入。因为批量**存入**用的是早已存在的 `hacd` 模式，所以能正常跑，**掩盖了产物过期**。

**修法**：同步二进制 + 在启动自检中加入**模式可用性检查**（对每个模式以空参数调用，捕获 `unknown mode`）：

```
modes = OK (8)          # 正常
modes = MISSING redeem-hacd   # 产物过期，自检即报
```

> 教训：`bin/` 下的二进制是**构建产物**，改完 `hacds_txbuild.rs` 必须重新 `cargo build --release` 并**同步到 `wallet-app/bin/`**，否则症状是「部分功能正常、部分静默失败」，极难定位。

### 4.20 Electron 不含 sha3-256（D53）

**现象**：索引器接入后应用**启动即崩**：

```
Error: Digest method not supported
    at fnSelector (indexer.js:34)   // crypto.createHash('sha3-256')
```

**根因**：`sha3-256` 在**独立 Node 里可用，但 Electron 的 Node 运行时不含该摘要算法**。同一份代码 `node indexer.js` 正常、`electron .` 直接抛错——属「开发能跑、打包即崩」。

**修法**：自研 `keccak.js`（纯 JS、零依赖、BigInt 实现 Keccak-f[1600] + FIPS-202 `0x06` 填充），Node / Electron 行为一致。

**验证**：官方测试向量 `SHA3-256("abc") = 3a985da7…c0e4f2a` ✅；7 个借贷函数 selector 与 Node `crypto` 参考值 **7/7 一致**，且与 txbuild 生成的交易字节一致。

> 教训：**凡是用到 Node 内置 crypto 的地方，都要在 Electron 里实测一遍**。Electron 的 BoringSSL 与 Node 的 OpenSSL 支持的摘要集合不同。

### 4.21 单位统一：HAC 用 HAC，hacds 用 atoms（D55–D56）

**背景**：旧代码把合约的 **zhu** 值直接显示（`bal:hac` 9.5 HAC 显示成 `9.5`、池 HAC 腿 9 zhu 显示成 `9`），
且池状态卡与协议状态**同一份数据两处渲染口径不同**（一处 raw、一处 ÷1e8），造成「池 hacds 3 vs 300,000,000」这类自相矛盾。

**约定（D55）见 §0.2**（唯一口径，取代 D37 的 zhu 展示口径）。理由：日常几乎不用 zhu，显示它只会让人看不懂；hacds 侧与浏览器/交易所 raw 口径保持一致。

**实现**：
- 新增 `hacOf(zhuVal)` —— HAC 显示（÷1e8 + ` HAC` 后缀）；**所有** `zhu()` 显示点替换为它。
- 新增 `hacInputToZhu(str)` —— HAC 输入 → zhu（`Math.round(v × 1e8)`；非数字/负数返回 null）。
- OPS 新增 **`hacFields`** 声明「以 HAC 计价的字段」；`buildCallParams()` 统一构造 params：
  - `swap_hac_to_ds` → `hacFields:['hac_in']`
  - `swap_ds_to_hac` → `hacFields:['min_out']`（**输出腿是 HAC**，滑点保护也以 HAC 计）
  - `add_liquidity` → `hacFields:['hac_amt']`（**这正是 D56 错配的那一腿**）
  - `loan_borrow` / `loan_repay` → `hacFields:['hac']`
  - `min_out`（swapH2D）/ `ds_in` / `ds_amt` / `share` 保持 atoms
- 字段默认值同步改人类单位（`hac_in` `1000000`→`1`；`ds_in` `1000000`→`100000000`）。
- 标签显式标单位：`投入 HAC 积分（HAC）`、`投入 hacds（atoms）`、`最少得到（atoms，0=不限）`。

**D56 池子单位错配（实测事故）**：首注 `add_liquidity(9, 300000000)` —— hacds 腿 3e8 atoms 正确，
但 HAC 腿**填 `9` 而非 `9e8`**，等于只注入 **9e-8 HAC**。证据：`isqrt(9 × 3e8) = 51,961 = lpt:tot`（吻合）；
若本意 9 HAC 应为 519,615,242；`pool_price = 3e-8`（应 ~1.376）。后果：hacds→HAC 报价恒为 ~0。

**处理**：`remove_liquidity(51961)` 全额退出 → `amm:hac / amm:ds / lpt:tot` 同时归零，未触发防尺度守卫。
退款：`due` +3 hacds、`bal:hac` +9 zhu。

> **教训**：`add_liquidity(hac_amt, ds_amt)` 两腿量纲**不同**（zhu vs atoms），是最容易犯的 1e8 倍错误 —— `hacFields` 机制即为杜绝它而设。

### 4.22 索引器服务端化（D57）

**为什么要服务端**：扫链既慢又耗流量（实测串行 2.6 块/秒，回溯 500 块要 3 分钟）。
放服务端后，钱包（PC / Android）**只调一次 `GET /watchlist`**，不本地扫链 —— 对手机尤其关键。

```
全节点 :8082 ──GET──► hacds_indexer.py :8124 ──GET /watchlist──► 钱包
```

**产物**（`hacds_exchange/indexer/`）：

| 文件 | 说明 |
|---|---|
| `hacds_indexer.py` | 单文件、零第三方依赖、Python 3（仅标准库） |
| `hacds_indexer.service` | systemd 常驻单元 |
| `部署说明-索引器.md` | 部署文档 |

**HTTP API**：

| 路径 | 说明 |
|---|---|
| **`GET /watchlist`** | ★ 钱包唯一需要的接口（概况 + 台账快照含健康度） |
| `/snapshot` `/health` `/sync` `/watch/add` `/watch/remove` | 辅助接口 |

**关键实现点**：

1. **`sha3` 用标准库** —— Python 3.6+ 内置 `hashlib.sha3_256`，**不像 Electron 的 Node 缺该算法**（对比 D53）。
2. **并发扫块** —— `--workers`（默认 4）。实测 **2.6 → 6.6 块/秒**（100 块 38s → 15s）。节点侧全是只读 GET，不受 sandbox per-IP 并发限制。
3. **增量同步** —— 记 `lastScanned`，之后每轮只扫新增块（60 秒 ≈ 2~3 块），几乎无感。
4. **台账落盘 + 手工增删** —— `watch.json`；合约早期无历史时可直接补地址。
5. **原子写盘** —— `tmp + os.replace`，避免写坏台账。

**钱包侧接入**：网络栏新增「索引器」输入框（`cfg.indexer`）。

- 填了 → 只调 `/watchlist`（清算页显示 `索引器在线，高度 N，台账 M`）
- 留空 / 不可达 → **自动回退本地扫块**（慢但可用，D51 的本地索引器保留）
- 所有 `liq:*` IPC 都返回 `source: 'server' | 'local'`，UI 会标注来源

**自检**（`selftest`，11 项全过）：sha3 官方向量、7 个 selector、kind=44 匹配（含正确排除其他 DApp）、清算判定边界（0/999/150/200/250）。

### 4.26 HACD 点对点转账（D63）

**背景**：「链上转账」页此前只有 HAC / hacds / 其它资产三项，**缺 HACD**。

**关键事实（已从 fullnode 源码核实）**：HACD 点对点是**链上一级转账**，不经过合约。

`base/src/iface/action.rs` 决定何时触发合约钩子：

```rust
let authorize = from.is_scriptmh() || from.is_contract();
let receive   = to.is_contract();
if !authorize && !receive { return Ok(None); }   // 普通地址 → 普通地址：不调钩子
```

因此：

| 场景 | 合约钩子 | 证书 | 一笔几颗 |
|---|---|---|---|
| **HACD 转他人**（我 → 对方） | **不触发** | **不需要** | **最多 200** |
| HACD 存入合约 | `PayableHACD` | 需要 | 1 颗（gas 限制） |
| 从合约赎回 | `PermitHACD` | 需要 | 1 颗 |

**实现**：复用官方钱包的 WASM SDK 本地签名，只把 `tx_body` 交给节点广播。

- 官方来源：`github.com/hacash/wallet` → `static/webwallet/lib/hacash_sdk.{js,wasm}`
- 引到 `wallet-app/vendor/`（2 个文件，291KB），**必须同步进 `package.json` 的 `files` 白名单**（否则静默失效）
- `wallet-app/hacd-transfer.js`：主进程侧封装（加载 WASM + 调 `hacd_transfer`）
- `main.js`：IPC `tx:hacdTransfer`；`preload.js` 暴露 `api.hacdTransfer`
- 渲染层：`OPS` 新增 `trHacd`（`tab:'xfer'`，`kind:'hacdTransfer'`）

**私钥不出主进程**：与 `hacds_txbuild` 同一条安全路径。实测 `hacd_transfer` 的 `from_pass`
**既接受口令、也接受 64 位私钥 hex**（两者签名结果一致），故直接喂 keystore 解锁后的私钥。

**手续费**：输入框默认值 = `0.0002 HAC × 颗数`（用户习惯的余量）；**清空则按节点费率自动估算**（复用 `fee.js`）。

> ⚠ 实测交易字节数**几乎不随颗数增长**（1 颗 162B、20 颗 298B），fee 只取决于总字节数。
> 按颗数给余量在颗数多时会明显多付（20 颗时约为节点要求的 17 倍）。清空走自动可避免。

**调用签名（wasm-bindgen）**：

```js
hacd_transfer(chain_id: BigInt, from_pass, fee_pass, to_addr, diamond_name_list, fee, timestamp: BigInt)
```

> ⚠ `chain_id` 与 `timestamp` **必须是 BigInt**（传 `0` 会报 `Cannot convert 0 to a BigInt`）；`fee` 不能传空串。

**验证**：真实节点 `/util/transaction/check` 通过，节点识别为
`Transfer 2 HACD (…) from … to …`（kind 6 `TransferHacdFromTo`）；1/2/5/20 颗均 `ret:0`；
打包副本（asar 解出后）内 WASM 可加载并构建成功。

### 5.1 为什么舍去「本地拉起预言机」（D4）

1. **原理上对普通用户无意义**：合约 `cfg:oracle` 只认一个固定地址（`1H3sFZ53…`），只有持有该私钥的一方签出的证书才被接受。用户本地跑预言机，签出的证书合约不认。
2. **预言机已在服务器部署并连通**（`43.251.101.101:8123`，实测 `/health` 正常），无需每台客户端再跑一份。
3. **免去 Python 依赖**：原方案 A 需目标机装 Python；方案 B 需用 Node 重写评分算法（风险高）。舍去后 App 只需 HTTP 即可，**零额外依赖**。

**附录**：`bin/hacds_oracle.py` 是早期随包的预言机脚本，App 代码**从不引用它**（已核实），实现 v0.2 时应从包中移除。运营方的预言机继续在服务器独立运行。

**打包注意事项（踩过的坑，必须遵守）**：
- `package.json` 的 `files` 白名单**必须**包含所有被 `require` 的本地模块（曾漏 `keystore.js`、`fee.js` → 启动崩溃）。**新增模块后必须同步白名单**。
- `bin/` **不能**进 asar（asar 内文件无法 `spawn`），必须走 `extraResources` → `process.resourcesPath/bin`
- 路径判断用 `app.isPackaged`，不要用 `fs.existsSync` 猜
- **改完必须用打包版实测**（`HACDS_SELFTEST=1`），不能只测开发模式
- **生产依赖会整个进 asar**：只用 `npm install` 装过、但最终用 vendor 副本的库，**要 `npm uninstall` 掉**，否则 node_modules 被打包（曾把 qrcode-generator 全打进去）
- 渲染层局部库（官方 SVG、二维码）放 `renderer/vendor/`，走 `renderer/**` 白名单，不依赖 node_modules
