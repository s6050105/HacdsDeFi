## 1. 定位与目标

**是什么**：Android 版 HacdsDeFi 客户端——**冷热共用钱包 + DeFi 控制台**。

**宣传口径（D-A1，同 PC）**：
> ## 冷热共用钱包 + DeFi 控制台
> **冷端离线构建/签名，热端联网查询/广播。**

⚠️ **限定**：冷端=离线（仅构建未签名体 + 签名）；热端=联网（查询/图样/证书/翻译/广播）。**不可**宣传"离线也能查余额/看图/兑换"。

**与 PC 版的关系**：功能对等，交互适配移动端。**不追求界面一致**（Android 用原生 Kotlin），但**交易构建/签名/协议行为必须逐字节一致**（共用同一份 Rust 引擎）。

**与 PC 的定位差异**：手机天然是冷端 → **Android 把"离线优先"提升为一等形态**（见 4.4）。

## 3. 技术架构

### 3.1 总体（原生 Kotlin，D-A2）

**已定：原生 Kotlin 实现**（不用 WebView/Capacitor）。好处：界面与系统能力（Keystore/生物识别/相机）最贴合，APK 更小，无 WebView 兼容负担。代价：界面需重写（不与 PC 共用 HTML）。

```
┌──────────────────── Android App (Kotlin) ────────────────────────┐
│  UI 层：Jetpack Compose                                          │
│    · 底部导航、各功能页、订单/交易确认页                            │
│  ─────────────────────────────────────────────────────────────  │
│  业务层 (Kotlin)                                                 │
│    · 钱包管理（Android Keystore 加密）                             │
│    · 手续费估算、AMM 报价、HACD 评分（Kotlin 移植）                 │
│    · 网络：节点/预言机 HTTP 客户端（OkHttp）                        │
│  ─────────────────────────────────────────────────────────────  │
│  引擎层：Rust 库 (libhacds_txbuild.so, arm64-v8a)                 │
│    · 从 hacds_txbuild 抽出：build / sign / addr / combo            │
│    · 与 PC 版同一份代码 → 交易字节级一致                            │
└──────────────────────────────┬──────────────────────────────────┘
                               │ HTTPS
                               ▼
                  全节点 43.251.101.101:8082
                  预言机 43.251.101.101:8123
```

**引擎为什么仍用 Rust 库**：交易构建/签名复杂（200+ 动作、Type-3 线格式、手续费迭代），重写风险高；共用同一份 Rust 代码 → 与 PC **字节级一致**。Kotlin 重写 secp256k1 + Type-3（BouncyCastle）**正确性难以保证**（low-S、确定性签名、编码细节）。

> **备选（若 Rust 库化受阻）**：Kotlin 用 BouncyCastle 实现 secp256k1 + 自研 Type-3 编码。**不推荐**——需与 PC 版逐字节交叉验证，工作量大、风险高。优先走 Rust 库。

**HACD 评分算法**：PC 版已移植为 JS（60/60 验证）。Android 侧**再移植为 Kotlin**（同一份算法，用 PC 版 JS 交叉验证），或直接调 Rust 库（若库化时一并纳入）。

### 3.2 Rust 库化改造（关键工作项）

现状：`hacds_txbuild` 是 **CLI 二进制**（`fn main()` 读 argv）。Android 需要**库**。

**改造方案**：抽出 `lib.rs`，暴露 C ABI 或 JNI 接口：
```rust
// 伪代码
#[no_mangle] pub extern "C" fn hx_build(req_json: *const c_char) -> *mut c_char
#[no_mangle] pub extern "C" fn hx_sign(unsigned_hex: *const c_char, key_hex: *const c_char) -> *mut c_char
#[no_mangle] pub extern "C" fn hx_addr(key_hex: *const c_char) -> *mut c_char
```
- 输入/输出用 **JSON 字符串**（简单、跨语言无歧义）
- 保留 CLI 入口（PC 继续用），**新增 lib target**（Android 用）
- 交叉编译：`rustup target add aarch64-linux-android` + NDK 链接器
  ```
  CARGO_TARGET_AARCH64_LINUX_ANDROID_LINKER=<NDK>/…/aarch64-linux-android21-clang
  cargo build --release --target aarch64-linux-android
  ```
- 产物 `libhacds_txbuild.so` 打进 APK 的 `jniLibs/arm64-v8a/`

> **风险评估**：这是 Android 版最大的不确定项。需先做**打通性验证**（能编出 .so + 能从 Java 调用 + 与 PC 结果一致）再全面铺开。

### 3.3 私钥存储（Android 特有，重点）

PC 版用 Node `crypto`（scrypt+AES-256-GCM）+ 文件。Android 上**增强**：

| 方案 | 说明 | 采用 |
|---|---|---|
| **Android Keystore** | 系统级硬件-backed 密钥（TEE/StrongBox） | ✅ **首选** |
| EncryptedSharedPreferences | Jetpack Security，AES256-GCM + Keystore 主密钥 | ✅ 次选 |
| 复用 PC 的 keystore 格式（文件） | 与 PC 完全兼容，可互相导入 | ✅ 兼容层 |

**拟设计**：
- **默认**：私钥用 **Android Keystore 保护**（生成一个不可导出的 AES 主密钥，用它加密钱包数据）——比 PC 的密码派生更强（用户不设密码也安全）
- **兼容**：仍支持导入/导出 PC 版 `keystore.json`（scrypt+AES-GCM），实现 **PC↔手机钱包互通**
- **生物识别**：解锁钱包时可要求指纹/面容（`BiometricPrompt`），作为可选项
- **离线机建议**：飞行模式 + 不导入网络配置

> 安全边界（与 PC 一致）：私钥只在本进程内存解密；构建时传给 Rust 库（进程内 FFI，**不落盘、不经网络**）。

### 4.3 二维码离线签名流（Android 亮点）—— 分片方案（D-A3）

```
离线机(手机)                              联网机(另一台)
 构建交易 ──┐
            ├─→ 显示【分片二维码】 ──依次扫码──→ 拼回完整 hex ─→ 广播
 签名    ──┘   (第1/3、2/3、3/3…)                    (需节点)
```

**为什么分片**：一笔交易的 `signed_tx_hex` 可能上千字符（尤其 combo 多动作、HACD 多颗），**超出单张二维码容量**。

**分片设计**：
- **分片**：把 hex 按固定大小切块（如每片 ~800 字符，留二维码纠错余量），生成 `N` 张二维码
- **包格式**：每片带**序号 + 总数 + 校验**（如 `HXDS/<seq>/<total>/<crc>/<data>`）
- **扫描**：接收端逐张扫 → 收齐后按序号拼回 → **校验 CRC** 通过才使用；缺片提示"还差第 X 片"
- **循环/手动**：发送端自动轮播，或手动"下一片"；接收端可乱序扫
- **容量估算**：QR 版本 40、纠错 L，最多约 2900 字节 → 单张可放约 2800 字符 hex；交易超此即分片
- **落文件兜底**：二维码不便时（如隔空传输），仍支持**导出/导入 hex 文件**

### 4.4 离线优先形态（D-A5）

**已定：Android 版也做"离线优先"形态**——手机天然适合当冷端。

| 形态 | 说明 |
|---|---|
| **冷端模式（离线优先）** | 应用可**完全不配置网络**（不填节点/预言机）也能使用：创建/导入钱包、构建未签名体、签名、生成二维码、导出文件 |
| **热端模式** | 配置节点/预言机后，解锁全部联网功能（查询、图样、证书、翻译、广播） |
| **双机协作** | 手机作冷端（构建+签名+二维码）↔ 另一台作热端（扫码+广播） |

**实现要点**：
- **网络配置可留空**：启动时不强制填节点；未配置时联网入口**灰显并提示**
- **界面自适应**：无网络时只显示"构建/签名/钱包"相关页；配置后其余页解禁
- **权限最小化**：不申请不必要的网络/后台权限；`INTERNET` 权限仅在热端用到时才需要（冷端纯离线可不用）
- **飞行模式友好**：全程无网络调用也能完成"构建→签名→出码"

> 这与 PC 版的 D23（离线签名工作流）同源，但 Android 把它提升为**一等形态**（PC 上离线是"一种模式"，Android 上离线是"可默认的使用方式"）。

### 4.5 HACD 多选与批量（D39，移动端适配）

PC 用 Ctrl/Shift 多选；**移动端无修饰键**，改为：

| 操作 | 行为 |
|---|---|
| **长按**钻石卡 | 进入多选模式并勾选该卡；工具条切换为「已选 n / 全选 / 取消 / 复制名称 / 批量存入」 |
| 单击（多选模式内） | 切换勾选（替代 Ctrl 单击） |
| 全选 / 取消 | 对**当前筛选+排序后**的可见集合整体操作 |
| 复制名称 | 按当前顺序、**逗号分隔**写入剪贴板（交易标准 `names` 格式） |
| 批量存入 | 跳到「存入兑换」页并填进 `names` 输入框 |

> **一致性要求**：复制出的字符串、填入的 `names`、以及最终交给 Rust 引擎的参数，**必须与 PC 逐字节一致**（同排序顺序、同逗号分隔、同大写）。勾选集在筛选/排序/切换地址时同样需要重排与清空。

### 4.6 单笔 HACD 存入 ≤1 颗（D40/D41，关键约束）

⚠️ **协议级硬约束，Android 端必须同样遵守。**

三桶硬上限（与 `gas_max` 无关，完整表见 PC §0.3）：`compute = 18,009` / **`resource = 6,100`** / `storage = 111,911`。

**结论**：
1. 「存入兑换 hacds」**单笔最多 1 颗**；多颗**拆成多笔**。
2. **原子交易（combo）不能绕过** —— 共享同一笔 gas 预算。
3. `names.length > 1` 时**必须弹确认**（同 PC）。
4. **提高 `gas_max` 或手续费无效**。

> 与 4.3 的**分片二维码**无关：分片解「码容量」，单桶上限解「链上执行预算」，互不影响；但离线流里同样「一笔最多 1 颗」。

### 4.7 批量转入 / 批量赎回（D43，移动端适配）

PC 侧实现：勾选多颗 → 一键「批量存入兑换 / 批量赎回」→ **自动拆成「每笔 1 颗」的独立交易并逐笔广播**（`tx:redeemBatch`）。

Android 侧**同功能**，但交互与流程适配移动端：

| 项 | 说明 |
|---|---|
| 入口 | 多选模式工具条（见 4.5）上的「批量存入 / 批量赎回」 |
| 拆分 | 同 PC：N 颗 → N 笔单颗交易 |
| 广播 | **热端**：逐笔 `POST /submit/transaction`；**冷端**：逐笔构建+签名后进**分片二维码队列**（见 4.3），由热端扫码逐笔广播 |
| 进度 | 逐颗显示 `[i/n] NAME ✔/✘`，失败可单独重试（移动端建议提供“重试失败项”） |
| 节流 | 同 PC，逐笔间隔 ≥120 ms，避免瞬时并发过高 |
| 成功判据 | `ret:0` 仅为进入 mempool；以 `due` / 钻石归属变化为准 |

**实现要点（与 PC 逐字节一致）**：
- 同 timestamp 的多笔交易 **hash 互不相同**（Hacash Type-3 **无 consensus nonce**，唯一性由 `hash_with_fee` 决定），因此可安全地一次性构建 N 笔后再逐笔广播。
- 传给 Rust 引擎的参数（`names`、证书流 126B/份、`ts`）必须与 PC 完全一致。
- **不提供**「合并成一笔」的选项——原子交易共享同一 gas 预算，照样超 6,100。

### 4.8 hacds 口径：全端 atoms（D44，必须遵守）

**口径见 PC §0.2**（唯一口径）。Android 侧同样**全端用 atoms**，不做 ÷1e8 换算：

| 区域 | 口径 | 字段 |
|---|---|---|
| 只读展示 | **atoms** | 已持有 hacds、待领取 hacds；协议状态的 `amm:ds` / `pendDs` / `stakedDs` / `treDs` / `loan:coll` |
| 可写输入 | **atoms** | 转账数量、`ds_in` / `min_out` / `ds_amt` / `share` |

- **必须用 `BigInt` 级别的整数类型**（Kotlin `Long` 不够——总供给 5.96e15 已超 `Long` 安全范围边缘，用 `BigInteger` / 字符串处理）。
- 副标题需注明口径，**不能**把 raw 值直接标成「个」。
- **别在输入框旁显示「个数」**：界面若出现两个口径，用户按个数读数去填 atoms 框，少写一个零就是 1e8 倍资金误差。标签写明 `atoms`。
- **交易所接口**：读 `serial=2000` 的 `amount` = raw atoms；个数 = `amount / 1e8`。合约与链上数据无需改动。

### 4.9 清算 / 结算模块（D51，移动端适配）

PC 侧三块：① LP 奖励结算 ② 金库清扫 ③ 借贷清算台。Android 同功能，交互适配：

| 块 | 移动端做法 |
|---|---|
| ① LP 奖励 | 一个按钮调 `lp_harvest`，走既有交易确认页 |
| ② 金库清扫 | 显示 `tre:hac` / `tre:ds`；「清扫」= 普通转账到金库地址（合约自动扣减 `tre:`） |
| ③ 借贷清算台 | 台账列表（卡片式，屏小不用表格）；可清算项高亮 + 「清算」按钮 |

**索引器放哪** —— 这是移动端与 PC 的核心差异：

| 方案 | 说明 | 建议 |
|---|---|---|
| **A. 随端索引（同 PC）** | 手机自己遍历区块建台账 | ⚠️ 耗流量/电量，遍历几百块 = 上千次 HTTP |
| **B. 服务端索引（推荐）** | 索引跑在服务器，App 只拉现成台账 | ✅ **推荐**；手机只发 1 次请求 |
| **C. 手工台账** | 用户自己填地址 | 兜底，零成本 |

> 倾向 **B**：索引器本质是「扫链」，属服务端职责。App 侧只需 `GET /liq/watchlist` 拿 `[{address, health, debt, coll}]`。若暂不搭服务端，先上 **C** 并保留 A 作为可选。

**清算判定必须与 PC 一致** —— `loan_status` 返回值语义与判据见 **PC §0.4**（可清算 ⟺ `debt > 0 && 0 < health < 200`）。

### 4.10 SHA3-256：Kotlin 侧注意（D53）

PC 侧的索引器需要 `sha3_256(函数名)[0:4]` 算合约函数 selector。踩到的坑：**Electron 的 Node 运行时不含 `sha3-256`**（独立 Node 有），导致「开发能跑、打包即崩」；PC 侧改为自研纯 JS Keccak。

**Android 侧同样注意**：
- **不要**用 `java.security.MessageDigest.getInstance("SHA3-256")` —— Android 各版本对 SHA-3 的支持不一致（API 35 前多数设备取不到）。

### 4.11 单位统一：HAC 用 HAC，hacds 用 atoms（D55，必须遵守）

**口径表见 PC §0.2**（唯一口径）。

**⭐ `add_liquidity(hac_amt, ds_amt)` 两腿量纲不同** —— 这是最容易犯 **1e8 倍**错误的地方（PC 侧已实际发生过一次事故：HAC 腿填 `9` 而非 `9e8`，等于只注入 9e-8 HAC，池价被压到 3e-8）。

Android 侧实现要点：
- 建两个 helper：`hacToZhu(hac: BigDecimal)` / `zhuToHac(zhu: BigInteger)`；hacds 侧**不做任何换算**。
- 在每个合约调用处**显式声明**哪些参数以 HAC 计（对应 PC 的 `hacFields`），不要靠参数名猜。
- 特别注意 **`swap_ds_to_hac` 的 `min_out` 是 HAC 腿**（输出腿），而 `swap_hac_to_ds` 的 `min_out` 是 hacds 腿（atoms）。
- 输入框标签必须显式标单位，如「投入 HAC 积分（HAC）」「投入 hacds（atoms）」。
- 若索引器放服务端（方案 B），Kotlin 侧根本不需要 sha3 —— **这是选 B 的又一个理由**。
- 若必须本地算，随包一个纯 Kotlin Keccak-f[1600]（约 120 行），**不要依赖平台实现**。

> 通用教训：凡平台内置 crypto 的摘要/曲线，**必须在目标运行时实测**，不要假设与桌面 Node 一致。

### 4.12 索引器服务端化（D57，移动端首选）

**不要在手机上扫链。** 实测扫描吞吐：串行 2.6 块/秒，并发 4 为 6.6 块/秒；回溯 500 块要 15~75 秒，
且产生数千次 HTTP 请求 —— 对手机的流量与电量都不可接受。

**正确形态**：索引器跑在服务端（`43.251.101.101:8124`），App 只发**一次**请求：

```
GET http://43.251.101.101:8124/watchlist
→ { ret, head, watched, withDebt, liquidatable, snapshot:[{address,health,debt,coll,liquidatable,noLoan,...}] }
```

清算页三块（LP 奖励 / 金库清扫 / 借贷清算台）中，**只有第三块需要索引器**；前两块直接查合约即可。

**实现要点**：
- 索引器地址放**设置项**（可留空）；留空或不可达时 UI 应明确提示「未连接索引器」，而不是静默空白。
- `/watch/add` `/watch/remove` 也走服务端，保持台账唯一（否则 PC 与手机各存一份会不一致）。
- 移动端**不要**实现本地扫链兜底 —— 服务不可用时应提示用户，而非暗中消耗流量。
- Kotlin 侧因此**完全不需要 sha3**（selector 计算在服务端完成）。

### 4.13 借贷额度提示与借贷状态常驻卡（D58 / D61，移动端适配）

**口径见 PC §0.4**（唯一口径），本文只讲移动端形态。**核心目的：借款前不必试错。**

**两张操作卡下方的实时提示**（对应 PC 的 `loanHintUpdate`）：

| 卡 | 填什么 | 实时显示 |
|---|---|---|
| 「借出 HAC」 | 借款额（HAC） | 可借上限、当前抵押价值、**本笔需抵押 ≥ X atoms（≈ Y HAC 价值）**，并判定 ✔ 可借 / ✘ 超上限 |
| 「追加抵押」 | 抵押额（hacds，atoms） | 本笔 ≈ X HAC 价值、**追加后总可借 Y HAC** |

**首页常驻「借贷状态」卡**（对应 PC 的 `#ovLoan`）：解锁后**一直在首屏顶部可见**，不必进借贷页、不必滚动。显示 6 项：
债务 / 抵押 / 抵押价值 / 抵押率 / **可借上限** / 清算状态（安全 · 可清算 · 无债务）。

**实现要点**：

- **不额外打链**：复用「协议状态」那一次调用已有的 `amm:hac` / `amm:ds` / `loan:debt_of` / `loan:coll_of`，本地算，输入即更新。
- **金额用 `BigInteger`**（见 4.8）：`coll × amm:hac` 这类乘法会溢出 `Long`。
- 抵押率公式 = `coll_hac × 100 / debt`；`debt = 0` 显示 `—`（合约哨兵 `999`）。
- 清算状态判定 = **`debt > 0 && 0 < health < 200`**（与 4.9 的清算台同一判据）。

> ⚠ **易误读，界面上要标清**：**200 是「清算线」，不是「50% 抵押率」**。
> 可借上限 = 抵押价值 ÷ 2 = **50% 抵押率**；「抵押率跌破 200」与「债务超过抵押价值的一半」是**同一约束的两种说法**。
> —— PC 侧已在常驻卡标题挂标签 `50% 抵押率` 消除歧义，Android 建议同样处理。

### 4.14 加流动性两侧联动（D62，移动端适配）

合约 `add_liquidity(hac_amt, ds_amt)` 的份额规则是 `share = min(lpttot×hac/ph, lpttot×ds/pd)`。
**两腿比例不匹配时取小的那侧算份额，多注的那侧白送进池子。**

移动端的键盘输入更容易出错，所以要做得比 PC 更"抢手"：

| 场景 | 行为 |
|---|---|
| 池内比例 | 卡片上显示「池内比例 X HAC ↔ Y atoms」 |
| 改一侧 | **立即自动填另一侧**（`ds = hac_zhu × pd / ph`；`hac = ds × ph / pd`） |
| 两腿不匹配（>1 单位） | 红字告警 + 给出配平值 |
| 首注 | 提示两侧自定，并预估份额 `isqrt(hac × ds)` |

**实现要点**：

- **注意输入法组合期**：Android 中文/数字输入法在拼字过程中会连续触发 `input`，
  联动要避开组合期（`isComposing`），否则会把用户正在输入的数字顶掉。
- **金额用 `BigInteger`**（见 4.8），`hac × pd` 这类乘法会溢出 `Long`。
- **取整容差**：下取整必然差 1 个单位，不算不匹配。

### 4.15 HACD 点对点转账（D63，移动端适配）

HACD 点对点是**链上一级转账**（kind 6 `TransferHacdFromTo`），**不经过合约、不需要证书**，
一笔最多 200 颗。完整原理见 PC 文档 4.26。

**Android 侧实现要点**：

| 项 | 说明 |
|---|---|
| 本地签名 | 复用官方 WASM（`hacash_sdk.wasm`）——**WASM 在 Kotlin/Compose 里跑不了**，需走 WebView 承载（同 D-A7 的 HACD 图样思路），或等 Rust 引擎补 `hacd-to` |
| 私钥边界 | 私钥不得进 WebView。建议：WebView 只做「字节拼装」，签名仍由 Rust/原生侧完成 |
| 输入 | 钻石名逗号分隔；收款地址 |
| 默认手续费 | `0.0002 HAC × 颗数`（与 PC 一致）；**留空则按节点费率自动估算** |
| 一次多颗 | 最多 200 颗，**不必拆笔** |

> ⚠ 注意与「存入合约」区分：存入合约受 resource 单桶 6,100 限制，**一笔只能 1 颗**；
> 点对点转账**没有这个限制**。UI 文案必须写清，否则用户会误以为也要一颗一颗转。
