# HACDS 索引器 · 服务器部署说明

> 目标服务器：`<your-server-ip>`（已运行 Hacash 全节点 + 预言机）
> 索引器脚本：`hacds_indexer.py`（单文件，零第三方依赖，Python 3）

## 0. 结论先行：索引器是**只读消费者**

- 它只做一件事：**GET 全节点 RPC**，遍历区块把「调用过借贷函数的地址」收集成台账。
- **从不提交交易**（代码中无任何 `/submit` 调用）、**不需要私钥**、**不需要余额 / gas**。
- 它与预言机（`hacds_oracle.py`，8123）**互不依赖**，可各自独立启停。

```
全节点 :8082 ──GET──► hacds_indexer.py :8124 ──GET /watchlist──► 钱包（PC / Android）
```

## 1. 为什么需要它（不能靠合约枚举）

合约**无法枚举借款人** —— 三个已核实的事实：

| 尝试 | 结果 |
|---|---|
| 合约有没有借款人列表 / 注册表？ | ❌ 借款账目按 `loan:debt:<addr>` **拼键**存储 |
| 合约会不会写日志？ | ❌ 无 `log_push` |
| 节点能否按前缀枚举合约 KV？ | ❌ `debug contract/storage` 只支持**精确 key** |

所以只能**遍历区块**，从历史交易里把借款人挖出来。

## 2. 原理（已验证的链上原语）

```
1) GET /query/block/intro?height=N&tx_hash_list=true
      → 该块的交易哈希列表
2) GET /query/transaction?hash=H&action=true
      → 结构化动作 [{kind, ...}]
3) 合约调用 kind=44，其 codes 内含 selector = sha3_256(函数名)[0:4]
      → 用借贷函数 selector 白名单过滤；命中则 tx.main_address = 借款人
```

字节码形态为 `09 14 01 <sig4> ee`（由 `hacds_txbuild` 实际生成的交易验证 3/3）。

### ⚠️ 关键语义：`loan_status` 的返回值**不是**健康度百分比

| 返回值 | 含义 |
|---|---|
| `0` | 无借贷、无抵押 |
| `999` | 有抵押但**无债务**（安全） |
| 其它 | `coll_hac × 100 / debt`（抵押率 × 100） |

清算门槛来自合约 `loan_liquidate`：要求 `debt > coll / COLL_RATIO(2)` 才放行，
即 `coll_hac / debt < 2` ⟺ **`health < 200`**。

> **可清算 ⟺ `debt > 0 && 0 < health < 200`**

（初版曾误写成 `health < 10000`，把「无借贷」标成「可清算」；已修正并有自检覆盖。）

## 3. 服务器前置

- Python 3（**仅标准库**：hashlib / hmac / json / struct / urllib / http.server / threading）
- 可访问的全节点 RPC

> **扫描吞吐（实测）**：串行约 2.6 块/秒（每块 = 1 次 block/intro + 每个 tx 1 次查询），
> 并发 `--workers 4` 约 **6.6 块/秒**。首次回溯 500 块 ≈ **75 秒**；之后每轮只扫新增块（60 秒一轮 ≈ 2~3 块），几乎无感。
>
> ⚠️ 注意：**必须确认节点 API 端口**。本机开发环境是 `8082`，
> 脚本默认却是 `127.0.0.1:8082`；若服务器不同，启动时显式传 `--node`。

## 4. 放置与启动

```bash
sudo mkdir -p /opt/hacds-indexer
# 上传脚本（从开发机 scp，或直接粘贴）
sudo cp hacds_indexer.py /opt/hacds-indexer/
sudo chmod 755 /opt/hacds-indexer/hacds_indexer.py
cd /opt/hacds-indexer

# 自检（离线，含 sha3 官方测试向量 + selector + 清算判定）
python3 hacds_indexer.py selftest          # 应输出 SELFTEST PASSED

# 先跑一次扫描看效果（前台，Ctrl-C 退出）
python3 hacds_indexer.py scan --node http://127.0.0.1:8082

# 常驻服务
python3 hacds_indexer.py serve --node http://127.0.0.1:8082 --port 8124 --interval 60 --workers 4
```

## 5. 参数说明

| 参数 | 默认 | 说明 |
|---|---|---|
| `--node` | `http://127.0.0.1:8082` | 全节点 RPC |
| `--contract` | `T1A8kaeWqK6wMUw5UMHCA6tMQ1iBdECyH` | 合约地址 |
| `--state` | `./watch.json` | 台账落盘路径 |
| `--window` | `500` | **首次**回溯块数。⚠️ 2000 块 ≈ 4000 次 HTTP，很慢；增量同步后每轮只扫新增块 |
| `--port` | `8124` | HTTP 服务端口 |
| **`--host`** | **`127.0.0.1`** | 监听地址。**默认仅本机**；要对外必须显式传 `0.0.0.0` |
| **`--read-only`** | **开启** | 默认禁用写接口（`/sync`、`/watch/add`、`/watch/remove`） |
| **`--allow-write`** | — | 显式关闭只读模式，启用写接口（无鉴权，谨慎） |
| `--interval` | `60` | serve 模式轮询秒数 |
| `--workers` | `4` | 并发扫块线程数。**实测**：串行 ~2.6 块/秒，并发 4 → **~6.6 块/秒**（100 块 38s→15s） |
| 环境变量 `HACDS_CORS_ORIGINS` | 空 | CORS 来源白名单，逗号分隔。留空 = 不发 CORS 头（默认即安全） |

> ⚠ **C-1 修复重点**：`--host` 与 `--read-only` 的**默认值**是安全的那一侧。
> 也就是说「什么都不传直接启动」= 只听本机 + 只读，不会出现
> 「按文档部署却把写接口暴露到公网」的情况。
>
> 需要写能力时（如钱包端增删台账），按需组合：
> ```bash
> --host 127.0.0.1 --allow-write      # 只给本机钱包用（推荐）
> --host 0.0.0.0   --read-only        # 公网只读（推荐）
> --host 0.0.0.0   --allow-write      # ⚠ 公网可写，必须自行加鉴权/防火墙
> ```

## 6. HTTP API

| 路径 | 说明 |
|---|---|
| **`GET /watchlist`** | ★ **钱包唯一需要的接口**：概况 + 台账快照（含实时健康度） |
| `GET /snapshot` | 仅台账快照 |
| **`GET /backing`** | ★ **运维监控**：合约内部积分 vs 真实链上余额（见 §10） |
| `GET /health` | 存活探测（返回当前高度、台账地址数） |
| `GET /sync` | 立即同步一次 |
| `GET /watch/add?address=…&note=…` | 手工加观察地址 |
| `GET /watch/remove?address=…` | 移除观察地址 |

> ⚠ 写接口（`/sync`、`/watch/*`）**默认关闭**。要启用必须显式传
> `--allow-write`（见 §9 安全说明）。`/watchlist`、`/snapshot`、`/backing`、
> `/health` 是只读的，任何时候都可用。

`/watchlist` 返回示例：

```json
{
  "ret": 0, "head": 792523, "watched": 3, "withDebt": 1, "liquidatable": 1,
  "snapshot": [
    { "address": "1...", "health": 150, "healthPct": 1.5, "debt": 1000,
      "coll": 300000000, "liquidatable": true, "noLoan": false,
      "first": 792100, "last": 792500, "calls": 4, "fns": {"loan_borrow": 1} }
  ]
}
```

## 7. 以 systemd 常驻（可选）

### 7.1 先建专用用户（M-6：不再以 root 运行）

索引器只读节点、只写自己的台账与日志，没有任何理由要 root。

```bash
sudo useradd --system --no-create-home --shell /usr/sbin/nologin hacds
sudo mkdir -p /opt/hacds-indexer
sudo cp hacds_indexer.py /opt/hacds-indexer/
sudo chown -R hacds:hacds /opt/hacds-indexer

sudo touch /var/log/hacds-indexer.log
sudo chown hacds:hacds /var/log/hacds-indexer.log
```

> 台账默认落在 `/opt/hacds-indexer/watch.json`（脚本同目录），已包含在
> 单元文件的 `ReadWritePaths` 里，在 `ProtectSystem=strict` 下仍可写。

### 7.2 安装服务

```bash
sudo cp hacds_indexer.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now hacds-indexer
sudo systemctl status hacds-indexer
tail -f /var/log/hacds-indexer.log
```

### 7.3 单元文件里的安全加固

| 指令 | 作用 |
|---|---|
| `--host 127.0.0.1 --read-only` | 显式写明安全默认值，不依赖代码默认 |
| `User=hacds` / `Group=hacds` | 降权运行（原为 root） |
| `NoNewPrivileges=true` | 禁止提权 |
| `PrivateTmp=true` | 独立 `/tmp`，防符号链接攻击 |
| `ProtectSystem=strict` | 全盘只读，只有 `ReadWritePaths` 可写 |
| `ProtectHome=true` | 看不到 `/home`、`/root` |

改完单元文件后记得 `sudo systemctl daemon-reload && sudo systemctl restart hacds-indexer`。

## 8. 钱包端配置

在钱包顶部网络栏的「**索引器**」输入框填 `http://<your-server-ip>:8124`（或留空）。

- **填了** → 清算页只调一次 `/watchlist`，**不本地扫链**（推荐；手机端尤其重要）
- **留空 / 服务不可达** → 自动**回退本地扫块**（慢，但可用）

清算页会显示索引器状态：`索引器在线，高度 N，台账 M` 或 `索引器未连接（将本地扫块，较慢）`。

## 9. 安全说明

- 索引器**无写权限**、无密钥、不含任何签名逻辑。即使被完全控制也动不了资金，
  只能污染视图（清算台名单）。
- **默认只听 `127.0.0.1`**，**写接口默认关闭**。要对外提供服务必须显式：
  ```bash
  --host 0.0.0.0 --allow-write    # 只读场景不要加 --allow-write
  ```
  systemd 单元里也要相应传参 —— 漏传就是「按默认配置部署 = 安全」。
- **CORS 改为来源白名单**（不再 `*`）。写接口是 GET（CORS 简单请求，免预检），
  配 `*` 时任意网页都能跨站触发 `/watch/remove` 把借款人从清算台移除。
  白名单通过环境变量配置：
  ```bash
  HACDS_CORS_ORIGINS=https://hacds.com,https://www.hacds.com
  ```
  留空 = 不发任何 CORS 头 = 浏览器端一律拒绝跨站读取（默认即安全）。
- 台账文件 `watch.json` 由**服务端**持有；钱包的增删会写回服务端（若已配置索引器）。
- **状态文件损坏时拒绝启动**（不再静默清空）：宁可起不来，也不要带着空台账跑，
  否则历史借款人会集体从清算台消失且日志一句不提。

## 10. 运维监控：`/backing`（积分覆盖率）

### 10.1 为什么需要

`loan_borrow` 是「**积分先行、转出在后**」：

```fitsh
// 1) 先给借款人记 bal:hac 积分
self.wr_ln_field(debtwho, 0, debt + hac_amt)
self.wr_u128("tot:debt", ... + hac_amt)
self.settle_and_write(main, 0, bal + nom)     // ← 创建积分
// 2) 同笔 TransferHacFromTo(合约 → 借款人) 经 PermitHAC 扣减放行
```

**如果借款人借款后不转出**（或转出失败但积分已记），那部分就以积分形式
滞留在合约里，等于「对合约 HAC 的索取权」。

### 10.2 副作用：利用率被低估

```
providers() = tot_hac_eff + lendable_amm_hac
utilization  = tot:debt / providers
```

积分让 `tot:hac` 变大 → `providers` 变大 → **利用率偏低 → 利率被低估**。

实测（初始 providers=10000、debt=3000、借 1000）：

| 情形 | tot:hac | providers | 利用率 |
|---|---:|---:|---:|
| 正常转出 | 10000 | 10000 | **40.0%** |
| 未转出 | 11000 | 11000 | **36.4%** |

低 3.6 个百分点，对应利率差约 1.5 个点。

**经济上可接受**——钱确实还在合约里、随时可兑付，只是显示口径偏低。
但运维必须能看见。

### 10.3 接口

```bash
curl -s http://127.0.0.1:8124/backing | python3 -m json.tool
```

```json
{
  "ret": 0,
  "tot_hac_eff": 100000000000,
  "real_hac": 200000000000,
  "ratio_bps": 5000,
  "ok": true,
  "note": ""
}
```

| 字段 | 含义 |
|---|---|
| `tot_hac_eff` | 合约内部有效积分总量（**zhu**，1 HAC = 1e8 zhu） |
| `real_hac` | 合约地址的真实链上 HAC 余额（**zhu**） |
| `ratio_bps` | `tot_hac_eff / real_hac`，万分比 |
| `ok` | `ratio_bps ≤ 10000` |

### 10.4 判读规则

| ratio_bps | 状态 | 处理 |
|---:|---|---|
| ≤ 9500 | 正常 | 无需干预 |
| 9500–10000 | 接近满额 | 留意借款人的转出习惯 |
| **> 10000** | **异常** | **立即告警**：有人凭空多了索取权 |

`ratio_bps > 10000` 意味着合约内部记的积分超过了真实持有的 HAC，
即**兑付缺口**。可能是：
- 借款人集体不转出（正常但极端）
- `total_add`/`total_sub` 漏记（代码 bug）
- 有人找到了凭空造积分的方法（安全事件）

### 10.5 为什么不在合约里算

`balance_coin(BURN_ADDR)` 返回的是 **Bytes**，不是 u128：

```
[diamond: 4B][satoshi: 8B][hacash: Amount 可变长编码]
```

`Amount` 是「单位 + 尾数」结构（`value:unit` = `value × 10^(unit−248)` HAC），
在合约里拆它既费 gas 又容易写错（Hacash 单位有 216/224/232/238/240/244/248 多档）。

索引器直接查节点 `/query/balance` 拿现成的人类可读金额，简单可靠。

### 10.6 接入官网

Worker 已加路由：

```js
if (p === '/api/backing') return { origin: IDX, path: '/backing' };
```

官网 `app/index.html` 的协议状态栏会显示「储备覆盖」一格：

- ≤95% 正常色
- 95–100% 黄色
- **>100% 红色 + 控制台告警**

悬停可看 `tot_hac_eff` / `real_hac` 明细。索引器不可用时显示「不可用」，
**不影响其他面板**（`refreshBacking()` 独立刷新）。

### 10.7 监控建议

在服务器上加一条轻量巡检（systemd timer 或 cron，每 10 分钟）：

```bash
#!/bin/bash
r=$(curl -s --max-time 5 http://127.0.0.1:8124/backing)
ratio=$(echo "$r" | python3 -c 'import sys,json; print(json.load(sys.stdin).get("ratio_bps",0))')
if [ "$ratio" -gt 10000 ]; then
  echo "[ALERT] hacds 储备覆盖率 ${ratio}bps > 10000" | systemd-cat -p err
fi
```

## H-2：按地址账本键的续租（v2.0 新增）

### 为什么需要

合约的 `rent_keys_group()` 只覆盖 23 个**固定键**（`amm:hac`、`tot:ds` 等），
但真正决定单个用户能否操作的**按地址键**无法枚举：

```
bal:hac:<addr>   due:<addr>        loan:debt:<addr>
loan:coll:<addr> loan:last:<addr>  lpt:<addr>
chk:hac:<addr>   chk:ds:<addr>     lch:hac:<addr>
lch:ds:<addr>    bad:<addr>
```

键过期后 `storage_load` 会 **abort `StorageNotActive(108)`**，该用户的
存款/取款/swap/赎回/还款**全部整笔回滚**。合约无管理员，没人有义务救他；
普通用户也不会拼键名。

### 索引器提供的接口

| 端点 | 返回 | 用途 |
|---|---|---|
| `GET /rent_keys` | 按长度分组的原始键字节（hex） | 一次拿全部 |
| `GET /rent_batches?max=10` | 已切成 ≤10 键的批次 | 直接喂 `rent_keys` |

`blob` 是**连排的原始键字节**，可直接作为合约 `rent_keys(blob, klen, period)` 的 `keys` 参数。

示例返回：

```json
{
  "ret": 0,
  "groups": [
    { "klen": 25, "count": 6,  "blob": "6475653a<21B hex>...", "keys": ["..."] },
    { "klen": 29, "count": 6,  "blob": "62616c3a6861633a<21B>...", "keys": ["..."] }
  ],
  "total": 22
}
```

### keeper 脚本示例

```bash
#!/bin/bash
# 每 6 小时跑一次：拉批次 → 逐批构造 rent_keys 交易 → 广播
IDX="http://43.251.101.101:8124"
NODE="http://43.251.101.101:8082"
PERIOD=300

curl -s "$IDX/rent_batches?max=10" | jq -r '.batches[] |
  "\(.klen) \(.blob)"' | while read klen blob; do
    # 构造 rent_keys(keys, klen, period) 调用
    # 用 txbuild 的 call 模式，参数：0x$blob(bytes) klen period
    ./hacds_txbuild call <keeper_addr> <ts> <contract>         rent_keys "0x$blob:bytes,$klen:u128,$PERIOD:u128"
    # 签名并广播（略）
done
```

### 合约侧参数

| 参数 | 值 | 说明 |
|---|---:|---|
| `RENT_PERIOD` | 300 | 续租期（≈104 天） |
| `RENT_MAX_KEYS` | 10 | 单笔上限（storage 桶 111,911） |
| `RENT_REWARD_HAC` | 0.07 HAC/键 | keeper 报酬 |
| 单批上限 | 10 键 | 与合约 `return 60` 对齐 |

### 运维检查清单

- [ ] 索引器 **持续运行**（它的 `watch` 台账就是活跃地址清单）
- [ ] keeper 定期拉 `/rent_batches` 并续租
- [ ] 监控：`storage_stat` 剩余租期 < 100 块时告警
- [ ] 新用户首次操作后，索引器应在下一轮扫描纳入台账

> ⚠ 索引器停止运行 = 新用户地址不进台账 = 无人为他们续租。
>     这是 H-2 的残余风险：**索引器本身成为可用性依赖**。
