## 0. 为什么编译需要指定版本

`HacdsDeFi3000.fitsh` 调用了 HACD 只读视图，并声明了一个 RV64IM 计算内核：

```
hacd_number_batch / hacd_visual_gene_batch            （链上读基因）
function rv64im score_sum                             （批量评分内核）
```

这些都是官方 **v1.3.0** 才引入的（提交 `9bcda57927`，2026-11-01）。

**v1.2.5 及更早的 `fitshc` 会在编译期直接拒绝**，报：

```
Compile error: Error { kind: Fault, msg: "unknown function 'hacd_visual_gene_batch'", code: None }
```

注意这是**编译期**错误，不是运行期。所以「等块高到了就行」是错的 ——
必须换 1.3.0 的编译器。

## 4. 自检

### 4.0 评分内核的工具链坑（2026-11-11 实测）

内核 `score_sum.rs` 要编成 RV64IM RISC-V 裸机，**不是**普通 Rust 编译。两个 profile：

| profile | 编译方式 | 需要什么 |
|---|---|---|
| `rv64im` | 自定义 target JSON + `-Zbuild-std` | 需 **nightly**（或 `RUSTC_BOOTSTRAP=1`）+ `rust-src` |
| `rv64imc` | 内置 `riscv64imac-unknown-none-elf` + `-C target-feature=-a` | 只需 `rustup target add riscv64imac-unknown-none-elf` |

**当前用的是 `rv64imc`**（`score_sum.rs` 第 1 行 `// calc: profile = rv64imc`），
因为在本机 Rust 1.99 上 `rv64im` 走不通：

```
error: `.json` target specs require -Zjson-target-spec to be added to the cargo invocation
```

这个标志是 cargo 的**不稳定**特性，stable 通道直接拒绝：

```
error: the `-Z` flag is only accepted on the nightly channel of Cargo
```

装上 nightly（`rustup toolchain install nightly`）可以让纯 `rv64im` 编过去。
官方出包用的是 Rust 1.80，那时没有这条限制。

### 4.0.1 rv64imc 的已知限制是否影响我们 —— 不必担心

`fitshc-cli/src/recipe.rs` 头注释提到 rv64imc 链接的是**预编译 core**，可能带上：

- A 扩展指令（`core::sync::atomic` 被链接时）
- LLVM 在不可达路径上生成的 2 字节 `unimp`（全零）

针对本项目实测的结论是**不影响**：

1. **验证器逐条线性解码整段可执行段**，不是只扫可达路径
   （`vm/src/calc/verify.rs:135` 的 `push_stream`，`while off < bytes.len()`）。
   任何不合法编码都会在**部署时**就被拒绝，不会留到运行时才炸。
2. **`unimp` 不是错误，是 `Trap` 指令**
   （`vm/src/calc/decode.rs:656`：`0x0000` → `Inst::Trap`），可通过验证。
   而纯 `rv64im`（非 C）遇到 4 字节全零反而**直接报错**（同文件 1132 行）——
   C profile 在这里更宽松。
3. **实测产物里零字节都在不可达路径/数据区**：连续零段最长只有 3 个半字（6 字节），
   且 200 颗满载（4800 字节输入）实际执行，结果与参考实现完全一致。

所以「消除这条限制」不是必要动作；真正要防的是**评分语义漂移**，见 4.1。

### 4.1 部署 nonce 必须是 2

```bash
python - <<'PY'
import json
a = json.load(open('_build_v30/HacdsDeFi3000.deploy.json'))['action']
# 前 2 字节是 action kind(0x0028)，接着 21 字节部署者地址，再 4 字节 nonce
print('nonce =', int(a[2+42:2+42+8], 16))
PY
# 期望：2
```

**为什么必须是 2**：合约地址 = `0x01 ‖ ripemd160(sha3(部署者addr21 ‖ nonce4))`。

| nonce | 推出的地址 | 状态 |
|---:|---|---|
| 1 | `VKNwXFFMCEn9XfMrhyHhd5rHqBnEyM3m1` | **#2000 旧合约，链上已存在** |
| 2 | `T1A8kaeWqK6wMUw5UMHCA6tMQ1iBdECyH` | **#3000 目标地址** |

用 nonce=1 部署会被链上拒绝（`contract already exists`）。
而 `BURN_ADDR`（首注铸死份额的接收地址）必须等于合约自身地址，
所以 `nonce` 与 `BURN_ADDR` 是**硬耦合**，改一个必须改另一个。

### 4.2 字节码里应出现两个新的 ACTVIEW

```bash
python - <<'PY'
import json
from collections import Counter
b = bytes.fromhex(json.load(open('_build_v30/HacdsDeFi3000.deploy.json'))['action'])
names = {0x15:'hacd_smelt', 0x16:'hacd_number_batch',
         0x17:'hacd_visual_gene_batch', 0x18:'hacd_life_gene_batch'}
c = Counter(b[i+1] for i in range(len(b)-1)
            if b[i] == 0x06 and b[i+1] in names)   # 0x06 = ACTVIEW
for k, v in sorted(c.items()):
    print(f'  0x{k:02x} {names[k]}: {v} 处')
PY
```

期望看到 `hacd_visual_gene_batch: 4 处` 和 `hacd_number_batch: 4 处`：

| 调用点 | 次数 |
|---|---|
| `hacd_read_gene`（单颗，赎回用） | 1 |
| `batch_score_total` 单块分支（≤128 颗） | 1 |
| `batch_score_total` 双块分支（129..200 颗） | 2 |

注意 `hacd_smelt` **不应出现**——它一次返回 50 字节，
而 `hacd_visual_gene_batch`（10 字节）更省 resource，只需视觉基因+编号。

### 4.3 函数总数

`contractmap.json` 里应有 **144** 个函数（原本 140，本版新增 4 个内核相关函数）。

### 4.4 评分一致性差分测试（最重要）

合约里有**两条**评分路径，必须算出完全相同的分数：

- **存入**：`batch_score_total` → rv64im 内核 `score_sum`
- **赎回**：`score_of` → FitSH 的 `diamond_score`

只要两者对同一颗钻石给出不同分数，用户就会「存进去 X 分、赎回来扣 Y 分」，
这是真正的账本 bug，且部署后无法修复。

```sh
python -I _test/diff_test.py
```

它用 Python 严格照抄 FitSH 的 `shape/style/color/nameliteral/numberliteral`
逻辑（`_test/fitsh_score_ref.py`），生成 119 个用例（含随机、各分支边界、
199 颗与 200 颗满载），逐条与内核实跑结果比对。

期望输出：`全部通过：内核与 FitSH 参考实现逐条一致`。

> ⚠ 改动 `score_sum.rs` 或合约里任一评分函数后，**必须重跑这个测试**。

## 5. 部署前的硬性前提

**这两个条件必须同时满足，缺一不可：**

| 条件 | 说明 |
|---|---|
| 节点 ≥ **v1.3.0** | v1.2.5 的内置表里没有这 4 个函数 |

## 6. ABI 参考（官方实际实现，非我们最初的提案）

我们最初在 `安全审计/整改/VM-issue-增加读HACD基因内置.md` 里建议的是：

```
hacd_info(name: Fixed6) -> (life_gene: Fixed32, visual_gene: Fixed10, number: u64)   ← 未采纳
```

官方实际给的是**批量、返回 Bytes**：

| 视图 | 入参 | 出参（按输入顺序，无 count 前缀） |
|---|---|---|
| `hacd_smelt` | name list | 每颗 50B：`number(8) ‖ visual(10) ‖ life(32)` |
| `hacd_number_batch` | name list | 每颗 8B：`number` |
| `hacd_visual_gene_batch` | name list | 每颗 10B：`visual_gene` |
| `hacd_life_gene_batch` | name list | 每颗 32B：`life_gene` |

### 入参编码

```
count(u8) ‖ name × count      // 每名 6 字节，字母表 "WTYUIAHXVMEKBSZN"
```

实测：`WTYUIA` → `01 57 54 59 55 49 41`（7 字节）。

**fitsh 里必须写成 `1 ++ name`**：
- 字面量 `1` 编译成 `PU8`（1 字节）；
- 若写成 `1u128 ++ name`，u128 拼接会按**定长 16 字节**展开，wire 就错了
  （见 `vm/src/value/item.rs:331` 的 `scalar_bytes`）。

### 视觉基因的派生

由名字 + `life_gene[20..31]` 的十六进制半字节派生，第 0 字节被
`life_gene[31]` 覆盖 —— 见 `field/src/types/diamond.rs` 的
`diamond_visual_gene()`。这是铸币公式，**合约直接用，不再自己实现**。

## 7. 常见疑问

**Q: 只有 1.2.5 节点，等块高到 800,000 能行吗？**
不能。函数在 1.2.5 的内置表里不存在，编译器就过不了。

**Q: 用 1.3.0 编译，但节点还是 1.2.5，能部署吗？**
编译能过，但链上执行会失败 —— 需要处理该交易的节点认识这些函数。

**Q: v1.3.0 有官方二进制吗？**
2026-11-10 时**还没有**。GitHub 上只有 `1.3.0` 这个 git tag，
`releases/tags/1.3.0` 返回 404，最新的正式 Release 仍是 1.2.5（10-17）。
需要自己从源码编译。
