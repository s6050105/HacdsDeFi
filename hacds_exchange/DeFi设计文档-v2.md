## 2. 5 维评分算法（Diamond_Analyzer v0.1.1，完整复现）

以下规则逐条提取自 **Diamond_Analyzer v0.1.1**（当初交易所使用的版本，`lib/DiamondAnalyser.py`），合约与预言机将**逐条精确复现**。

> **基准切换说明（2026-10-19 项目方决定）**：评分标准由官方 hacds Java（`AnalyseDiamond.java` + `rule.txt`）切换为 Diamond_Analyzer v0.1.1。两者在 390 颗主网样本上仅 3 颗分差，全部归因于下文标注的三条规则差异（Right mix pure 条件、Number Symmetry 启用、改名项）。DA 版另有两处总体语义：**styles 位置规则为 elif 互斥链**（官方为独立 if 可叠加）；**总分下限 1 分**（0 分钻石抬为 1 分，api.txt Notes："All diamond scores less than 1 will be set to 1"）。等分并列时取**先命中者**（DA 按 append 顺序严格大于比较）。

### 2.1 数据来源

每颗钻石有三项链上固有数据参与评分：

- **名字**（6 字符，字母表 `WTYUIAHXVMEKBSZN`）——决定 nameliteral 维度与 visual_gene 的名字段；
- **可视化基因**（10 字节，由出生时的 `life_gene` 确定性派生，永久不变）——决定 shapes 与 styles/color 维度；
- **编号**（挖矿序号，1 起递增）——决定 numberliteral 维度。

visual_gene 派生算法（已用主网钻石 MVUUBA 在线验证吻合：`life_gene aa20...5a01 → visual_gene 019833c5b35b517105a0`）：

```
byte0    = life_gene[31]                                  // 形状字节
byte1..4 高半字节 = 名字 6 字符在字母表中的索引（hex）
byte4 低半字节..byte9 = life_gene[20..30] 各字节 % 16（hex）
```

### 2.2 四类规则与分值

**总分 = 形状分 + 颜色分（样式或颜色二选一） + 名字字母分 + 编号分**（官方实现：形状为 Common 时算「样式」，否则算「颜色」）。

### 2.3 链上实现要点

- 全部规则为**纯整数/字节比较**，无浮点、无外部调用——FitSH 可完整表达；
- 去重计数（两字母/三字母/四色/五色等）用 16 位 bitmap 实现（字母表/色板均 ≤16 种字符）；
- styles 位置规则按 elif 互斥链实现（首个命中生效）；
- `hacds = max(1, 总分) × 10⁸`（DA 总分下限语义，与官方发行量纲一致）。

## 3. 基因数据引入：技术事实与方案（新增决策点）

### 3.1 技术事实（全部已从 VM 源码逐条核实）

1. **基因确实是链上数据**：`DiamondSmelt.life_gene` 是钻石铸造时写入的全局状态，浏览器可查（如 MVUUBA 的 `019833c5b35b517105a0`），且由出生数据确定性派生、永久不变；
2. **但 HVM 视图层没有基因入口**：系统视图全表 17 项（balance_* / hacd_insc_* / hacd_name_list / hacd_owner_addrs / tx_message / tx_blob / check_signature / sigset_* / asset_meta），**没有任何一项返回基因或编号**。`hacd_insc_get` 只返回铭文内容——铭文路线已按你的指示整体排除；
3. **合约无法从链上自证基因**：这是 VM 能力边界，不是设计选择。

### 3.2 方案：预言机签名证书（推荐）

**核心机制**：项目方运营一个「基因证书预言机」账户，对每颗钻石的评分要素离线预签一份证书；存款人从官网/API 获取证书，随存款交易提交，合约用 native `verify_signature`（已核实：验任意 32 字节哈希 + 账户地址 + 97 字节 Sign wire）验证后记账。

**证书内容**（打包后取 sha3_256 作为签名消息）：
```
name(6B) + visual_gene(10B) + number_u64(8B) + score_u32(4B) + version(1B)
```
共 29 字节 → sha3_256 → 32 字节摘要 → 预言机账户签名（97 字节 Sign wire）。

**存款流程**（单笔 Type-3 交易，两动作）：
1. 动作1：`Message(证书 126 字节)` 附带证书（Message data 上限 65535 字节，可多证书连排；受 gas 三桶预算约束，**批量存款建议 ≤4 颗/笔**，见 4.2）；
2. 动作2：`TransferHacdTo(合约, 钻石名单)`——PayableHACD 钩子内：读取 tx_message → 解包证书 → `verify_signature` 验签 → **用证书里的 visual_gene 与 number 在链上重算 5 维评分，并与证书声称的 score 比对**，不一致拒绝 → 按 score × 10⁸ 记积分。

**关键设计：证书只引入「基因字节与编号」，评分永远链上重算**。预言机无法通过谎报分数作弊——它只能证明基因，不能决定分数。即使预言机作恶，最坏情况是提交错误基因字节（影响该钻石的形状/样式分），且任何人可对照浏览器公开数据发现并举报（管理员可暂停+换预言机）。

**为什么不用 Merkle 证明**：`merkle_root`/`merkle_multi_root` native 虽可用，但需要预言机维护全局基因 Merkle 树并逐笔签发证明路径，运营成本高于直接签名证书，且不提供额外安全性（两者最终都信任预言机账户的签名）。留作未来扩容选项。

### 3.3 备选方案（供对比）

| 方案 | 信任假设 | 运营成本 | 用户体验 |
|---|---|---|---|
| **A 预言机签名证书（推荐）** | 信任预言机账户诚实（可多签升级） | 低：一次性预签全量钻石证书，API 分发 | 存款多一步取证书 |
| B 管理员手动登记 | 信任管理员 | 高：每笔存款人工审核 | 差 |
| C 只用名称 1 维评分 | 无外部信任 | 零 | 好，但与官方分偏差大（v1 已否决） |

**预言机账户治理**：初始由项目方运营（与金库同权），合约内置 `set_oracle` 管理员函数可更换；升级路径为 M/N 多签（`sigset_at_least` 已核实可用）。

## 4. 账本存储架构（v2.1 新增：全部已从 VM 源码核实）

### 4.1 三种 KV 存储的生命周期与容量（源码事实）

| 存储 | FitSH 操作 | 生命周期 | 容量上限 | 租金 |
|---|---|---|---|---|
| global_map | `global_put/get` | **交易内易失**（VM 实例逐交易新建，回滚/回收即清空） | 40 键 | 无（但无意义） |
| memory_map | `memory_put/get/once/take/patch` | **交易内易失**（同上） | 24 键 | 无（但无意义） |
| status | `status_put/get` | 持久（链上状态） | **全表总载荷 ≤128 字节**（所有键+值合计） | 免租金 |
| storage | `storage_new/edit/load/stat/rent/recv/del/patch` | 持久（链上状态） | 每值 ≤1280 字节、每键 ≤128 字节 | **租金燃烧**（见 4.2） |

**结论**：用户余额账本、AMM 池状态、rpu 检查点、钻石库存索引——**全部只能建在 storage 上**；status 仅够放几个小配置（费率、暂停位、预言机地址指针等，合计 128 字节内）；global/memory 只能做单笔交易内的临时工作区（如批量存款的证书中转）。

### 4.2 storage 租金制（精确数学）

- **计价单位**：`unit = 值字节长 + 20`（`storege_value_base_size=20`）；租金按 `unit × 块数` 燃烧（gas 计）；
- **周期**：1 period = 100 块（`storage_period=100`，主网块间隔 300 秒 → 1 period ≈ 8.3 小时）；单次 `storage_new` 最多 30000 period（=300 万块 ≈ 28.5 年），`storage_rent` 续租同上限；recover（复活额度）上限 3000 period（≈2.85 年）；
- **过期语义**：live 额度耗尽 → 键进入 recoverable，`storage_load` **读取报错**（不是返回 nil）；live+recover 双耗尽 → 键物理删除。`storage_stat` 返回 nil（不存在）或 `(live剩余块, recover剩余块)` 二元组；
- **写入规则**：`storage_new` 只能创建不存在的键（存在即报错，含 recoverable 态）；已存在且 active 的键改值用 `storage_edit`（每次 edit 另收 `unit×4` 手续 gas）；**recoverable 键须先 `storage_rent` 补 live 额度复活**（`storage_recv` 补的是 recover 宽限额度，延长"过期后可抢救窗口"，不是复活）；
- **退款**：`storage_del` 退还未消耗 live 额度 + 键成本；`storage_edit` 改小值有按比例退款。

**对账本设计的影响（写入模式）**：每键写入必须走「`storage_stat` → nil 则 `storage_new` / 有 live 则 `storage_edit` / 仅 recover 则 `storage_rent` 复活后 `storage_edit`」三分支。

**单笔交易预算硬约束（v2.1 核实）**：gas 分三桶——compute / resource / storage，预算分别为 **18,009 / 6,100 / 111,911**（`compute_limit_byte=72`、`resource_limit_byte=56`、`storage_limit_byte=99` 查预算表），且**三桶在整笔交易内跨动作、跨钩子累计**（VM 实例逐交易新建、桶不重置）。含义：

- 一笔「转入 + 转出」互换交易里，Payable 钩子、Permit 钩子、评分计算、AMM 计算**共享**这 18,009 compute；
- 5 维评分估算 ~1,500 compute gas（几百次 2–12 gas 的整数/字节操作），单笔存款验 1 份证书 + 评分 + 记账绰绰有余；**批量存款建议 ≤4 颗/笔**（评分+验签×4 约 8,000–12,000 compute）；
- storage 桶 111,911：单键满租 30000 period 需 1024+36×30000 ≈ 108 万 gas，**单键单笔最多续约 3080 period（≈2.9 年），满租需分 ~10 笔**。余额键用**定长小值**（u128 积分 = 16 字节 → unit=36）控制租金；按 gas 计价折算（费率 0.001 HAC/300B 交易口径），单键 1 年租期（1051 period ≈ 38,860 gas）燃烧约 0.013–0.13 HAC（随交易费率与体积线性变化，费率下限 5×10¹⁰ u232/字节）。合约策略：新键一律 1 年期，续租由管理员批量交易执行（每笔 ~30 键）。

### 4.3 账本键设计（FitSH storage 键 ≤128 字节，值 ≤1280 字节）

| 键（字节串） | 值 | 说明 |
|---|---|---|
| `bal:hac:<addr21>` | u128（zhu 计） | HAC 积分余额 |
| `bal:ds:<addr21>` | u128（10⁻⁸ 计） | HACD/HACDS 统一积分余额 |
| `chk:hac:<addr21>` | u128 | HAC 奖励 rpu 检查点 |
| `chk:ds:<addr21>` | u128 | DS 奖励 rpu 检查点 |
| `tot:hac` / `tot:ds` | u128 | 总质押量计数器 |
| `rpu:hac` / `rpu:ds` | u128（×10¹² 定点） | 每单位累计奖励值 |
| `tre:hac` / `tre:ds` | u128 | 金库待清扫累积额 |
| `amm:hac` / `amm:ds` | u128 | AMM 池两侧存量 |
| `cfg:*`（status 表） | 小整数/地址 | 费率、暂停位、预言机地址、admin（合计 ≤128 字节） |

钻石库存**不逐颗建键**：库存即合约实际持有的 HACD（链上所有权即真相），赎回定价靠赎回人提交的证书（见 5 节），合约只维护 `tot:ds` 与钻石计数器（可选）。

## 5. 统一积分账本（同 v1，评分维度升级 + storage 载体）

| HAC | HAC 积分（以 zhu 计） | AMM 池价 |

- **手动选择**：钻石库存全局共享，转出动作里指名购买库存中的具体钻石，钩子按 `5维评分×10⁸` 扣积分；
- **赎回人同样提交证书**（v2.1 变更）：合约不逐颗维护库存钻石的评分记录（省租金与键位），赎回人从预言机 API 取该钻石证书、随赎回交易提交（Message 动作），钩子验签 + 链上重算评分定价。证书防伪由预言机签名保证，库存所有权由链上 HACD 余额保证，两者正交；
- **不做任何铭文判断**（已锁定）。

## 6. 互换模型（同 v1 + AMM 细化 + 自动补足）

三对方向全部支持，**单笔 Type-3 交易原子完成**（动作1转入 + 动作2转出）：

| 交易对 | 定价 | 手续费收取腿 |
|---|---|---|
| HACD ↔ HACDS | 5 维评分 ×10⁸ | HACDS 腿 |
| HACDS ↔ HAC | **AMM 恒定乘积池**（已锁定） | 输出资产 |
| HACD ↔ HAC | 上两条路径组合（一笔交易内完成） | HAC 腿 |

**AMM 池**：合约状态维护 HAC 池（zhu 计）与 HACDS 积分池两个计数器；恒定乘积 `x·y=k`，手续费 0.5% 进输出腿；首次流动性由项目方注入（部署后管理员直接转入 HAC 与 HACDS 作为种子）。

**自动补足（v2.1 统一原语）**：任一转出钩子发现用户积分不足时，自动经 AMM 池用另一积分补足差额（例：HACD 积分不够 → 用 HAC 积分按池价换入差额）。三对方向共用这一套换汇原语，每笔互换**恰收一次** 0.5%（补足腿与主腿合并计费，不重复收费）。

**手续费规则**：始终收在可分割腿（HAC 或 HACDS）。默认费率 0.5%（万分之 50），管理员可在 0–3% 内调整。

## 7. 质押与利息（同 v1）

**积分即质押**：持有 HAC 积分或（HACD/HACDS）积分就是质押。

- 每笔手续费按 **80/20** 切分：质押奖励池 / 金库（已锁定）；
- 奖励分配用「每单位累计值」（rpu）检查点法（Synthetix 模式），状态即 4.3 的 `rpu:*` / `chk:*` / `tot:*` storage 键：
  - 收费时：`rpu += 费用 × 10¹² / 总质押量`（总量为 0 时费用进待分配桶）；
  - 各账户余额变动时结算检查点，应得奖励 = 余额 × (rpu − 账户检查点)；
- **按费源币种发放**（已锁定）：HAC 手续费分给 HAC 积分持有者，HACDS 手续费分给（HACD+HACDS）积分持有者；
- 领取奖励 = 普通转出动作，钩子合并校验放行，无需单独交易。

## 10. 风险与限制（v2.1 更新）

1. **预言机信任**（最重要）：基因字节由预言机证书引入，评分虽链上重算，基因本身无法链上自证。缓解：证书同时含 score 供链上校验重算一致、浏览器公开数据可对照举报、`set_oracle` 可换、可升级多签；
2. **管理员权力**：费率、暂停、预言机更换均为管理员权限 → 建议尽早多签；
3. **AMM 种子流动性**：需项目方注入初始 HAC 与 HACDS；
4. **评分规则基准固定为 Diamond_Analyzer v0.1.1**：该版本已停更（当初交易所使用的版本），规则不会再变——这反而消除了「官方调整 rule.txt 需合约同步升级」的风险；若未来项目方决定换基准，合约与预言机需同步升级；
5. **storage 租金与 gas 三桶预算**（v2.1 新增）：账本键过期即读报错，合约需内置续租逻辑（管理员定期 `storage_rent` 批量续费）；单笔交易三桶预算 18,009 compute / 6,100 resource / 111,911 storage 且全交易累计共享——批量存款每笔 ≤4 颗钻石、单键单笔最多续 ~2.9 年；租金是持续运营成本（每键每年约 0.01–0.13 HAC 量级，随费率浮动），定价时计入；
6. **成本**：ContractDeploy 协议费 + Type-3 gas；存款/赎回均带证书，每颗钻石 126 字节。
