### 已执行并拦截

| # | 攻击 | 期望 | 实测 | 结果 |

### H16 详细：参考价操纵防护

**攻击方式：** 单笔大额 swap 把现货价砸低 55%

```
攻击前: spot = ref = 1,003,260,644
投入 50 亿 hacds 换 HAC 后:
  spot  = 448,892,592   （跌 55%）
  ref   = 1,003,932,054 （仅动 0.07%）
```

**双重防护生效：**

1. **EMA 限速**：单次最多走 `REF_WINDOW` 的 10%，理论上要 10 轮才能拉低 55%
2. **熔断**：现货偏离旧 ref 超过 ±20% 时，置位 `ref:paused`

**验证熔断后的借款：**
```
loan_borrow → error 51
源码: if self.ld_u128("ref:paused") != 0 { return 51 }   // 价格偏离熔断（H-1）
```

**结论：攻击者无法通过单块 swap 操纵抵押品估值。** 这直接保护了 H7（闪电贷式操纵）和 H12（参考价操纵）两条攻击路径。

## 9. 发现的问题

### 9.1 直接转账的 HACD 会永久锁死

**现象：** 合约实际持有 19 颗钻石，但 `hacd_count` 只有 10 颗。

**原因：** 挖矿奖励或直接转账到合约地址的 HACD 不触发 `PayableHACD` 钩子，不记账。

**影响：** 用户误操作会把资产永久锁在合约里。

**建议：** 前端明确提示「请勿直接向合约地址转账 HACD，请使用存入功能」。

### 9.2 txbuild 缺少 `hacd-from-to`

赎回需要从合约转出 HACD，而官方 `hacds_txbuild` 只支持 `hacd-to`（from 固定为交易主地址）。

**处理：** 已在测试版 txbuild 中补齐该子形式。

### 9.3 参考价初始化门槛导致小池不可用

`MIN_REF_POOL_HAC = 1000 HAC`、`MIN_REF_POOL_DS = 100亿`。初始池若低于该值，`ref_price` 永远为 0，借贷和清算全部不可用。

**这是设计意图**（防薄池钉价），但意味着**上线初期必须有足够深的池子**。

### 9.4 主网 serial 与测试网不同

- 主网：`serial 3000`，合法域 `1025 ≤ s ≤ 1025+(height−765432)`
- 测试网：`serial 5~816`（`asset_non_mainnet_min_serial=5`, `alive_height=0`）

测试网必须改合约常量才能发行，这是环境差异，不影响主网。

## 13. 补充：测试过程中的经验教训

### 13.1 踩过的坑（供后续测试参考）

| # | 坑 | 原因 | 正确做法 |
|---|---|---|---|
| 1 | 地址推导错误 | 自写 JS 实现与 Rust 不一致 | **必须用官方 `hacds_txbuild` 推导** |
| 2 | 交易大小超限 | 22,073 B > 16,384 | 瘦身到 15,936 |
| 3 | 分批部署不可行 | 合约无 `Append` 钩子 | 放弃该方向 |
| 4 | `fee_purity` 拒绝 | 节点默认门槛 6.024e9 | 测试网调低到 1e6 |
| 5 | 高度 288 后难度抬升 | 非主网 ASERT 调整窗口 | 改 `difficulty_adjust_blocks` |
| 6 | 挖不到钻石 | 前导零要求 1/17^10 | 环境变量降到 1/17^2 |
| 7 | 钻石竞价不启动 | `bider.rs` 硬编码要求 is_mainnet | 改源码放开 |
| 8 | 竞价账户无余额 | 竞价需要付费 | 转账充值 |
| 9 | `serial overflow` | 非主网合法域 5..5+height | 等高度或降低 serial |
| 10 | 池子被 swap 搞坏 | 大额单次 swap 改变价格 | **建池后不要做破坏性 swap** |
| 11 | `ref:paused` 置位 | 现货偏离 ref > 20% | 需等 300 块窗口恢复 |
| 12 | `hacd-from-to` 不存在 | txbuild 未实现 | 补测试版 |

### 13.2 三条关键原则

**① 所有金额必须确认单位**
- HAC = zhu（1 HAC = 1e8 zhu）
- hacds = atoms（decimal=0）
- 混淆单位会导致「余额不足」这类难以定位的错误

**② 建池是单向操作**
一旦建好，任何大额 swap 都会永久改变比例。**测试清算时不要用 swap 操纵价格**，应改用「借到接近上限 + 等利息侵蚀」的方式。

**③ 参考价有双重保护**
- EMA 限速：单次最多 10%
- 熔断：偏离 > 20% 暂停借款

这意味着**攻击者无法用单块交易操纵抵押品估值**，但也意味着**测试时很难主动压低参考价**。

```
单借款人上限  = providers × 20% = 260 HAC
```

抵押 519.72 HAC 价值（51.95 亿 due）后借满 260 HAC，实测：

```
loan_status = 200    ← 抵押率恰好 200%
清算线      = 160
```

### 14.2 为什么到不了清算线

借款有两个约束：

| 约束 | 公式 | 效果 |
|---|---|---|
| 200% 抵押率 | `debt ≤ coll_value / 2` | 抵押率 ≥ 200% |
| 单借款人上限 | `debt ≤ providers × 20%` | 防止单户集中 |

**只要 `debt ≤ coll_value / 2` 成立，抵押率就恒 ≥ 200%，永远高于 160% 的清算线。**

要突破这一层，只能靠**参考价下跌 20%**。但：

| 防护 | 效果 |
|---|---|
| EMA 限速 | 每 300 块最多走 10%，跌 20% 需 600+ 块 |
| 熔断 | 现货偏离 ref > 20% 时置位 `ref:paused`，暂停借款 |

### 14.3 实测：操纵价格被拦

投入 50 亿 hacds 砸盘后：

```
现货价 spot = 448,892,592   （跌 55%）
参考价 ref  = 1,003,932,054 （仅动 0.07%）
借款请求    → error 51（ref:paused 熔断）
```

### 14.4 结论

**清算机制在正常借贷路径下不会被触发，这是设计的成功。**

四层防护叠加：

1. **200% 抵押率** —— 借款时留 40% 价格缓冲
2. **20% 单借上限** —— 单户无法形成系统性风险
3. **EMA 限速** —— 单块最多 10% 价格变化
4. **20% 偏离熔断** —— 异常价格时暂停借款

**这意味着：正常用户不会被误清算，攻击者无法通过操纵价格制造坏账。**

### 14.5 遗留风险

清算路径（`loan_liquidate`）**代码未经实测**。虽然静态分析显示逻辑正确（清算人出资换抵押、奖励市场化、部分清算、坏账记 `bad`），但：

- 从未在链上执行过
- 涉及真实的资产转移
- 边界条件（`CLOSE_FACTOR_BPS`、`DEEP_TRIGGER_BPS`）未验证

**建议：主网上线后，在小额状态下观察首笔真实清算，或使用专门的测试链预置不健康仓位来验证。**

## 15. 🔴 关键发现：深水清算超出 resource 上限

### 15.1 现象

深水清算（抵押率 < 105%）执行时：

```
OutOfGas(31): resource gas limit exceeded: used 6174 > limit 6100
```

| 项目 | 值 |
|---|---|
| `gas_max` | 99（协议允许的最高档） |
| `resource` 上限 | **6,100**（`GAS_BUDGET_LOOKUP` byte 56） |
| 深水清算实际消耗 | **6,174** |
| 超出 | **74（1.2%）** |

### 15.2 影响

**深水清算路径在链上无法执行。**

触发条件：`coll_hac < debt × 105%`，即仓位穿仓。

后果：
- 清算人无法接管抵押品
- 债务清零逻辑走不到
- 合约停留在「穿仓但无法清算」的状态

正常清算（105% ≤ 抵押率 < 160%）受 `CLOSE_FACTOR_BPS` 限制只还 50%，gas 消耗更低，**可能不受影响**（未实测，因为构造该场景需要更精细的价格控制）。

### 15.3 这是一个真实的合约缺陷

不是测试环境问题：
- `gas_max = 99` 已是协议允许的最大值
- `resource` 上限由 `resource_limit_byte = 56` 决定，是共识参数
- 无法通过交易参数或节点配置突破

### 15.4 可能的修复方向

1. **精简 `loan_liquidate` 的深水分支**（当前 gas 超标 1.2%，微调即可）
2. **拆分深水接管为独立函数**（减少单个函数的 gas 峰值）
3. **降低深水分支的操作数**：例如取消 `apply_loss` 的瀑布计算

### 15.5 验证路径

在主网部署前，必须：
- 用 `hacds_audit_gas` 之类工具精确测量 `loan_liquidate` 各分支的 gas
- 或修改合约后重测

**这是本次测试最重要的发现，直接关系到合约能否安全上线。**

### 15.6 正常清算分支的 gas（未实测）

正常分支（105% ≤ ratio < 160%）受 `CLOSE_FACTOR_BPS` 限制只还 50% 债务，理论上 gas 消耗低于深水分支。

但**未能构造该场景**：价格变动是跳跃式的（一次 swap 让 ratio 从 167% 直接到 70.6%），无法精确落在 105%~160% 这个 55 个百分点的窄区间。

**结论：深水分支确定超限；正常分支未知，需专门工具测量。**

## 19. 🔴 第二个缺陷：深水清算算术下溢

### 19.1 现象

修复 gas 后重测深水清算：

```
Arithmetic(90): arithmetic sub check failed with U128(355393071) and U128(355393072)
```

两个数只差 1 —— **下溢 1 个单位**。

### 19.2 根因

```fitsh
var deep_nom = self.hac_to_nominal_up(deep_pay)   // ← 向上取整
if pbal < deep_nom { return 11 }
self.settle_and_write(payer, 0, pbal - deep_nom)  // ← 下溢点
```

`hac_to_nominal_up` 向上取整，得到的 `deep_nom` 可能比 `deep_pay` 大 1。
但 `pbal` 是精确的实际余额。

若 `pbal == deep_nom - 1`，检查 `pbal < deep_nom` 成立会返回 11。
**实测走了下溢而不是返回 11**，说明检查与实际扣款用了不同的值。

### 19.3 影响

深水清算在特定余额下会**直接 panic 回滚**，而不是优雅报错。

### 19.4 位置

`loan_liquidate` 深水分支，`settle_and_write(payer, 0, pbal - deep_nom)` 这一行。

### 19.5 修复方向

1. 扣款前重新读一次 `pbal`（避免读后被其他操作改变）
2. 或改用 `hac_to_nominal`（向下取整）保证不超扣
3. 或加 `if pbal < deep_nom { return 11 }` 的二次检查

| 借款 | ⚠ **被拒（return 40）**，原因见下 |

**为什么借款被拒**：`ref_price_of = 0`（参考价未初始化）。
借款估值走 `coll_to_hac_liq()`，用**保守价 `min(现货, 参考价)`**；
参考价为 0 时抵押价值算作 0，任何借款都超限。

参考价初始化有硬门槛（`MIN_REF_POOL_HAC=1,000 HAC`、
`MIN_REF_POOL_DS=100 亿 hacds`），本轮测试池只有 91 HAC / 9.1 亿 hacds，
**远未达门槛**。这是**正确行为**（防小额池被操纵），不是缺陷。

主网首注即要求该规模（见 `发行参数-正式.md`「池深门槛」一节），
所以借贷路径需要在建够深池后补测。清算路径同理。

### 本轮新发现的 Low 级问题（未修，记录备查）

**`swap_hac_to_ds(0, ...)` / `swap_ds_to_hac(0, ...)` 静默成功**

- **现象**：`in_amt = 0` 时返回 `0`（成功），而非拒绝
- **路径**：`fee=0` → `net_in=0` → `out = muldiv(pool_ds, 0, pool_hac) = 0` →
  `out < min_out` 不成立 → `out >= pool_ds` 不成立 → 写入 `amm:lastout = 0` → 返回 0
- **影响**：**无资金风险**（池子不变、用户余额不变）。唯一副作用是把
  `amm:lastout` 这个同笔交易内的临时通道置为 0
- **对比**：`add_liquidity(0, 0, ...)` 会正确返回 `2`（某侧为 0）
- **建议**：后续版本在 `amm_swap` 开头加 `if in_amt == 0 { return 2 }`
- **为什么本轮没修**：开发树已冻结，且这是零资金风险的语义瑕疵；
  在已定稿待部署的合约上为它重新编译、重新审计，代价大于收益

### 本轮发现的两个 `self_check` 位语义问题（建议下个版本修）

#### ① bit8（256）：把正常路径误判为异常

```
if self.ld_u128("tot:hac:") == 0 {
    if self.ld_u128("amm:hac") > 0 { r = r + 256 }
}
if self.ld_u128("tot:ds:") == 0 {
    if self.ld_u128("amm:ds") > 0 { r = r + 256 }
}
```

- **触发场景**：用户把**全部**存款投进 AMM。`tot:hac` 是用户存款总额，
  全部入池后必然为 0，而 `amm:hac > 0` 是同一笔钱的去处。
- **实测**：建池后 `balance_hac = 0`、`amm_reserves = 1e11`，
  `self_check` 立刻变成 `256`。这是**唯一 LP 的正常状态**，不是回绕后遗症。
- **影响**：运维监控会误报。若索引器按 `self_check != 0` 告警，会出现大量假阳性。
- **建议**：判定条件应改为「`tot` 归零但 `amm` **也**归零、其它侧仍有余额」，
  或干脆去掉 `amm` 分支（`amm` 与 `tot` 是互补的两侧，不能互为异常证据）。

#### ② bit9（512）：砸盘后长期置位

- **触发场景**：`ref_refresh` 检测到 `spot` 偏离旧 `ref` 超过 ±20% 时置
  `ref:paused = 1`，`self_check` 计 bit9。
- **实测**：砸盘 28.7% 后 `self_check = 512`，需要 EMA 多轮才能复原。
- **影响**：这是**设计内的正常熔断指示**，不是异常。但和 bit8 同处一个
  返回值里，运维脚本若按 `self_check != 0` 报警会混淆。
- **建议**：把「熔断中」这类**状态位**与「账目异常」这类**错误位**分开暴露，
  例如新增 `self_check_state()` 返回状态位，`self_check()` 只保留错误位。

两项均**不影响资金安全**：bit8 是误报，bit9 是设计内状态。
本轮未改合约（开发树冻结 + 合约不可升级），仅记录备查。

## 附三：`hacds` 资产别名与 serial 不一致（本轮发现并修复）

### 现象

测试网用 `txbuild transfer ... asset-from-to <from> <to> hacds <amount>` 领取
合约内的 hacds 配额，链上回：

```
[revert] address "T6itDyi..." asset is insufficient, at least 1000000000
```

但同一时刻 `/query/balance?address=<合约>&assets=true` 明确显示合约持有
`{"serial":6,"amount":5963298700000000}`（全部供给）。

### 根因

`testkit/src/txbuild.rs:47` 把 `hacds` 别名硬编码成**旧版** serial：

```rust
const HACDS_SERIAL: u64 = 2000;          // ← txbuild 侧
fn hacds_serial() -> u64 { HACDS_SERIAL }
```

而 #3000 版合约的常量是 3000（`HacdsDeFi3000.fitsh:168`）：

```fitsh
const HACDS_SERIAL : u128 = 3000
...
if serial != HACDS_SERIAL { return 1 }   // PermitAsset 校验
```

于是「`hacds` 别名 → txbuild → serial 2000 的转账动作 → 合约要求 3000 →
`asset_sub(2000)` 查不到余额 → 报 insufficient」。

实测确认：把参数从 `'hacds'` 换成数字 `'6'`（测试网 serial）后**当场成功**，
链上到账 10 亿 hacds。

### 影响面

`hacds_exchange/indexer/hacds_build_server.py`（官网 `/api/build`）第 101 行
把 `"hacds"` 列为合法别名并**原样转发**给 txbuild：

```python
ALLOWED_SERIALS = {"hacds", "3000"}
...
argv.append(sr)          # ← "hacds" 直接交给 txbuild → 变成 2000
```

这意味着：**任何走官网 `/api/build` 且用 `hacds` 别名的资产转账请求，
链上都会被合约拒绝**。用户侧只能看到「交易失败」，无从得知原因。

RPC 文档里恰好就教用户这么用：

```bash
hacds_txbuild transfer {main} {ts} asset-from-to {from} {to} hacds {amount}
```

即**文档指引本身就是错的**。

### 修复

在服务端把别名翻成数字 serial 再交给 txbuild（合约与 txbuild 均未改动）：

```python
HACDS_SERIAL_MAINNET = "3000"

def normalize_serial(sr: str) -> str:
    if sr == "hacds":
        return HACDS_SERIAL_MAINNET
    return sr
...
argv.append(normalize_serial(sr))
```

验证：`normalize_serial('hacds') -> '3000'`，`'2000' -> '2000'`，`'3000' -> '3000'`。

### 为什么改服务端而不是改 txbuild

`testkit` 属于 `hacash_fullnode` 仓库，与节点源码同源，改动会牵动完整重建与
主网节点二进制的一致性；而这个问题**只出在别名的翻译层**。
服务端是唯一把 `hacds` 这个**字符串**放进 argv 的地方——
PC 钱包与 Android 客户端都直接传数字 serial，不受影响。

### 仍需跟进（未改，记录备查）
