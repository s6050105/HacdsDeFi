## 2. 部署方案

### 2.1 为什么是「单笔部署」

| 方案 | 可行性 | 原因 |
|---|---|---|
| 原合约直接部署 | ❌ | 22,073 B > 16,384 |
| 分批部署（Deploy + Update） | ❌ | 见 2.2 |
| **瘦身后单笔部署** | ✅ | 15,936 B |

### 2.2 分批部署为何不可行

```rust
// vm/src/action/contract_exec.rs:177
// Authorization is intentionally delegated to the current contract's Change/Append hook.
let _ = run_abst_entry(ctx, sys_hook, caddr, Value::Nil)?;
```

`ContractUpdate` 的授权交给合约自身的 `Change`/`Append` 钩子。本合约只有 8 个**资产钩子**，没有 `Append` 钩子 → 更新被拒。

这是「完全取消管理员」设计的必然结果。想要可更新就必须有管理员，二者不可兼得。

另外实测：即使只部署钩子骨架，也会报
`abstcall 65: call target function 0x866bfdf6 not found` —— 钩子会调用 external 函数，缺了就无法通过验证。

### 2.3 瘦身内容

| 改动 | 节省 | 风险 |
|---|---|---|
| 删除 FitSH 五维评分实现（431 行） | 3,048 B | 赎回改走内核，需验证等价 |
| `BYTE_TABLE`(256B) → `buf_cut("" ++ n, 15, 1)` | 765 B | **wire 格式，重点验证** |
| `charge_fee_redeem` 合并进 `charge_fee_amm` | 小 | 需验证 `LP_BPS==REDEEM_LP_BPS` |
| `ref_price()` 内联 | 小 | 等价 |
| 删除 `pk_put`/`pk_zeros`/`bal_key` | 小 | 需确认调用点已替换 |
| 内核改用优化版 hcf1（2,026 B） | 1,674 B | **算法等价，已 15/15 验证** |

### 2.4 静态一致性核对（已完成）

| 检查项 | 结果 |
|---|---|
| 常量 | ✅ 56 个完全一致（仅 `BURN_ADDR` 为测试网地址） |
| 8 个资产钩子 | ✅ 齐全，签名未变 |
| 对外接口 | ✅ 仅少 `batch_score_quote`（调试用） |
| 费用分配 | ✅ `LP_BPS == REDEEM_LP_BPS == 8000`，逐行等价 |
| opt_v2 内核算法 | ✅ 15/15 测试向量通过 |
| 部署大小 | ✅ 15,936 ≤ 16,384 |
