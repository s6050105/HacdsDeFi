## 1. 身份

> ⚠ **#3000 的合约地址绝对不是 `VKNwXFFMCEn9XfMrhyHhd5rHqBnEyM3m1`。**
> 那是**旧版 #2000 的地址**（部署者 `15fv6...` + nonce=1），已在链上存在。
> 合约地址由「部署者 + nonce」唯一推导，nonce=1 已被占用，
> 重复部署会被拒绝：`contract <addr> already exists`
> （`vm/src/action/contract_exec.rs:41`）。

### 地址推导规则

```
合约地址 = VERSION_CONTRACT(0x01) ++ ripemd160( sha3(部署者addr21 ++ nonce4) )
```

源码：`vm/src/value/mod.rs:24 ContractAddress::calculate`

### 发行总量推导

```
全流通 HACD      = 138,540 颗
Σ评分            = 492,427
精确均值         = 492,427 / 138,540 = 3.55440306

分数单位总量     = 3.55440306 × 16,777,216（HACD 总发行量）
                 = 59,632,987 分

atoms 总量       = 59,632,987 × SCORE_SCALE(1e8)
                 = 5,963,298,700,000,000 atoms
```

### decimal=0 的含义

**1 atom 就是 1 个 hacds**，用户看到的数量和链上 atoms 完全一致。

配合 `SCORE_SCALE = 1e8`：

| 存入钻石 | 铸出 hacds |
|---|---|
| 1 分 | 100,000,000 |
| 3 分 | 300,000,000 |
| 10 分 | 1,000,000,000 |

全流通 HACD（138,540 颗）全部存入约 **4.92e13 atoms**，占供给的 0.83%。

**所以供给量是充足的** —— 总量 `5.96e15` 覆盖了「所有钻石按平均分存入」的理论上限。

## 3. 三处必须完全一致

这三处任何一个写错，后果都是资金级的，改不了（合约不可升级）。

| 位置 | 正确值 | 写错的后果 |
|---|---|---|
| `AssetCreate.supply` | `5963298700000000` | 链上发行量错误，无法补救 |
| 合约 `HACDS_SUPPLY` 常量 | `5963298700000000` | `return 53` 供应闸门失效 |
| 合约 `SCORE_SCALE` 常量 | `100000000` | 铸发量差 1e8 倍 |

**当前源码值**（已核对）：

```fitsh
const SCORE_SCALE   : u128 = 100000000
const HACDS_SERIAL  : u128 = 3000
const HACDS_SUPPLY  : u128 = 5963298700000000
```

> ⚠ 旧版本文档曾把 `HACDS_SUPPLY` 写成 `59632987`（少 1e8 倍）。
> 那是 decimal=8 时代的写法，**#3000 已不适用**。以源码为准。

### serial 合法性

- 规则（`mint-core/src/exec/asset.rs`）：`1025 ≤ serial ≤ 1025 + (height − 765432)`
- 高度 792,309 → 上限 27,902，**3000 在合法域内**
- 链上已占用：`{1025 HACP, 1026 TEXAUTH, 1027 HUSD, 1028 HACDS(他人), 1111 CARAT}`
- **协议不检查 name/ticket 唯一性**，只查 serial

> #1028 的 ticket 也是 `HACDS`（其 name 是 "HACD Fragments"）。
> 钱包/浏览器会显示同名，**请按 serial=3000 辨识**。

## 6. 部署后必做：首注 + topup

### 6.1 首注

调用 `add_liquidity(hac_amt, ds_amt, min_share, deadline)`。

首注会创建两类键：

| 类型 | 键 | 数量 |
|---|---|---|
| 固定键 | `amm:hac` `amm:ds` `lpt:tot` `tot:hac` `tot:ds` 等 | 24 个 |
| 地址键 | `u:<首注人>` `ck:<首注人>` `u:<BURN>` `ck:<BURN>` | 4 个 |

> `BURN_ADDR` 常量就是合约地址本身（`const BURN_ADDR`，值必须等于 §1 的合约地址），
> 首注铸 `MINIMUM_LIQUIDITY` 死份额时创建它的 `u:` / `ck:` 键。

**新键租期 `PERIOD_NEW = 100` 期 = 10,000 块 ≈ 34.7 天**（5 分钟/块，288 块/天）。

### 6.2 立刻 topup（关键）

首注后**必须立刻**跑一次 `topup_keys`，把键补到 `RENT_PERIOD = 300` 期（≈104 天）。

**为什么不能等 keeper 自动续：**

```
rent_keys 的续租条件：live < period/3 = 100 块
新键 100 期 → live = 10,000 块
10,000 < 100 ？ → False
```

**首注后 34.7 天内 `rent_keys` 完全不触发**（既不续也不付酬）。
这段窗口里唯一能救的是 `topup_keys`（不看阈值、直接补期、不付报酬）。

如果 34.7 天内没跑 topup 且 keeper 也没接手，键到期后**被物理删除**
（`storage_new` 的 `recover_credit = 0`，没有恢复窗口），
用户的余额 / LP 份额 / due 配额**永久归零**。

**执行命令：**

```bash
HACDS_KEEPER_KEY=/path/key.hex \
python3 hacds_exchange/indexer/hacds_keeper.py topup \
    --node http://43.251.101.101:8082 \
    --contract T1A8kaeWqK6wMUw5UMHCA6tMQ1iBdECyH \
    --main <首注人地址>
```

脚本自动覆盖：24 个固定键 + 4 个首注地址键，并按键型自动分批
（`u:` 5 键/批、`ck:` 4 键/批、固定键 10 键/批）。
成本约 **0.001 HAC**（不付 keeper 报酬，只有手续费）。

### 6.3 长期运维

topup 之后键的租期是 300 期，此时 `rent_keys` 的续租条件才成立
（`live` 会从 30,000 掉到 100 以下 → 触发续租 + 付酬 0.07 HAC/键）。

keeper 需要按 104 天一轮的节奏运行。报酬从合约 `tre:hac` 支出，
**不发 keeper 自己的钱**（keeper 只付交易手续费）。

## 7. 口径约定（UI / 交易所 / 合约三方一致）

**#3000 是 `decimal = 0`，没有 1e8 换算问题。**

| 场景 | 用什么 |
|---|---|
| 链上 `amount` | 原样，就是个数 |
| 交易所接口 | 原样 |
| 钱包展示 | 原样 |
| 合约内部账本（`due` / `amm:ds`） | 原样（atoms = 个数） |

**但仍要注意大整数**：总量 `5,963,298,700,000,000` 超过
`Number.MAX_SAFE_INTEGER`（9,007,199,254,740,991）。

- JS：用 `BigInt` 或字符串
- Kotlin：用 `BigInteger`（**`Long` 不够**）

> 旧文档 §2「口径约定」整节讲的是 decimal=8 的 raw atoms ÷ 1e8 分界，
> **#3000 已不适用**，这里替换为「原样处理 + 大整数」两条。
